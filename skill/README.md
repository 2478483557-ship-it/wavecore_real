# skill/ — 技能包（Skill）

> 赛题要求：把与大模型协作过程中沉淀的可复用经验提炼为技能包，占评分 15%。
> 评价标准是**可复用性**：一支陌生队伍拿到这个目录，能否直接用在自己的题目上。
> 每一条都要写明：适用场景、使用方法、失效条件，以及从哪些失败/观察中总结得出。

```markdown
- **失效条件**：什么时候这个方法不适用（边界要写清！）
- **来源**：从哪次失败/观察中总结的（日期 + 事件）

```

## 已录入条目

## SK-001：Vivado 中文注释乱码处理

- **适用场景**：.v/.sv 代码文件含中文注释，Vivado 编辑器或综合/仿真时中文显示为乱码；或 GitHub 上中文乱码
- **使用方法**：
  1. 原理：代码文件是 UTF-8 编码，而 Vivado（2020.1 及常用旧版）按系统 GBK 读取 → 中文乱码
  2. 本地开发用文件：把 .v 代码转成 **GBK** 编码（VSCode 右下角点编码 → "通过编码重新打开/保存" → GBK；或用 Python 批量转）
  3. 文档类（.md/.txt）保持 UTF-8 不动
  4. 上传 GitHub 前，把 .v 转回 **UTF-8**（仓库统一 UTF-8，跨平台才不乱码）
- **失效条件**：注释纯英文时无需处理；含 emoji 等 UTF-8 独有字符的文件转 GBK 会失败或丢字符（先删掉再转）
- **来源**：团队前期研究踩坑（2026-09-02 录入）
- **已验证效果**：前期项目中出现并已用此法解决

## SK-002：综合报 filemgmt 56-2 路径错误

- **适用场景**：Vivado 综合/导入时报 `[filemgmt 56-2]` 类路径错误（文件找不到/路径无效），且工程所在路径含中文、空格或位于网盘下载目录
- **使用方法**：
  1. 把整个 Vivado 工程放到**纯英文本地路径**，例如 `D:/fpga/wavecore`（不要放桌面中文路径、不要放 `D:/Total download/夸克下载/...` 这类含中文的目录）
  2. 工程名、模块名也用纯英文
- **失效条件**：路径已全英文仍报错 → 不是路径问题，检查文件是否真被拷贝全、`.xpr` 里引用的源文件路径是否失效
- **来源**：团队前期研究踩坑（2026-09-02 录入）
- **已验证效果**：前期项目中出现并已用此法解决

## SK-003：综合报 PID not specified

- **适用场景**：综合（或运行）时报 `PID not specified` 类错误，工程在网盘同步目录（百度网盘/OneDrive 等）或被杀毒软件拦截
- **使用方法**：
  1. 把工程移出网盘同步目录（网盘会锁文件/拦截 Vivado 的临时进程）

- **来源**：团队前期研究踩坑（2026-09-02 录入）

## SK-004：仿真报 cannot open xxx.mem（$readmemh 找不到文件）

- **适用场景**：仿真报 `cannot open sine_rom.mem` 或数据文件打不开——testbench 里用 `$readmemh("相对路径", mem)` 但 Vivado xsim 的工作目录不是工程根目录，相对路径失效
- **使用方法**：

## SK-005：DRC BIVC-1 Bank 电压冲突（同 Bank IO 电平标准必须一致）

- **适用场景**：实现阶段报 `[DRC BIVC-1] Bank IO standard Vcc: Conflicting Vcc voltages in bank xx`，例如"sys_clk (LVCMOS15) 与 key0 (LVCMOS33) 冲突"
- **使用方法**：
  1. 原理：FPGA 引脚按 **Bank** 分组，每个 Bank 有**同一个供电电压 VCCO**，同一 Bank 内所有 IO 必须用匹配该电压的电平标准（LVCMOS15 ↔ VCCO=1.5V、LVCMOS33 ↔ VCCO=3.3V），混用即报 BIVC-1
  2. 报错信息会直接告诉你哪两个端口冲突 → 把报错里提到的端口找出来
  3. **以官方例程 XDC 为准**：去资料盘找同类外设（按键/LED/串口/ADDA）的官方约束文件，抄它的 IOSTANDARD，不要凭感觉猜
  4. 达芬奇Pro 实例：sys_clk/sys_rst_n/key/led/beep/touch_key 全在 **bank34（1.5V 域）→ LVCMOS15**；AD/DA 模块（da_*/ad_*）与串口等在 **3.3V 域 → LVCMOS33**
- **失效条件**：若报错端口不在同一 Bank 却仍报 BIVC-1 → 检查 XDC 是否写错管脚号（管脚错位会把两个不同域的 IO 拉到一起）
- **来源**：WaveCore M3 真实踩坑（2026-09-03）：key0/LED 误标 LVCMOS33，DRC 抓出与 sys_clk 冲突；对照官方 XDC 修正为 LVCMOS15
- **已验证效果**：修正后 DRC 通过、布局布线正常

## SK-006：ILA 改探针后新探针（P2）在硬件里看不到

- **适用场景**：给 ila_0 加/改探针、重新生成 bit 并烧录后，ILA 波形窗口仍只有旧探针（如只有 P0/P1，没有新加的 P2/ad_cap）
- **使用方法**（按顺序排查，90% 是最后两条）：
  1. 确认 IP 真的改了：双击 ila_0 → Number of Probes / 宽度正确（最权威：看 `.xci` 里 `C_NUM_OF_PROBES`）
  2. 确认代码真的例化了新探针：`board_top.v` 里 `.probe2(ad_cap)` 存在
  3. 确认工程编译的是外部最新文件：Sources 里右键文件看路径，若在 `.srcs` 内=旧副本，Remove 后重新 Add
  4. 改 IP 后必须整套重跑：Synthesis → Implementation → Generate Bitstream（改了 IP 四步缺一不可）
  5. 烧录时**确认选的是最新 bit**：Program Device → Browse → 看文件修改时间（老 bit 没有新探针，这是最常见原因）
  6. 烧完看 **hw_ila 核的探针清单**（不是波形窗口）：展开 hw_ila_1，若清单里有 P2 而波形里没有 → 在波形窗口右键 **Add/Remove Signals** 勾选 P2（波形不会自动显示新探针！）
  7. 硬件核编号 hw_ila_1/hw_ila_2 是 Vivado 按顺序起的，**与 IP 名 ila_0 无关**，别被误导
- **失效条件**：若探针清单里始终只有旧探针 → 用 `reset_and_build.tcl`（reset 全部 run 强制无缓存重建）排除 OOC 缓存
- **来源**：WaveCore M4a 真实踩坑（2026-09-03），排查链：IP 配置→代码→工程引用→缓存→烧录文件→波形显示
- **已验证效果**：最终在波形窗口手动添加 P2(ad_cap) 后显示正常

## SK-007：UART RX 采样点错位导致收到乱码（命令无反应）

- **适用场景**：串口向下发命令（如 5A A5 帧）FPGA 完全没反应；或收到的字节总是乱的
- **使用方法**：
  1. 规则：UART 每位【边缘会抖动，只有中点最稳】，接收必须在每个数据位的**中点**采样
  2. 正确时序：检测到起始位下降沿 → 等**半位长**到起始位中点并复查 → 之后**每满一个完整位长(DIV)采一次** → 采样点 = 217、651、1085…（DIV=434 时）恰好各 bit 中点
  3. 错误写法（v1.0 踩过）：数据位也按半位长采 → 采样点 434、868… 全落**位边界** → 乱码
- **失效条件**：若采样点正确仍乱码 → 查波特率误差(50MHz/115200 取整 434 引入 0.006%，可忽略)、电平极性、信号同步
- **来源**：WaveCore M5a 真实踩坑（2026-09-03）：命令收不到，逐步推演位时序定位
- **已验证效果**：修正为满位长采样后，HEX 发 0x81 帧 LED 正确跳档（9/3 上板验证）

- **来源**：WaveCore uart_rx v1.1 同步时踩坑（2026-09-03）
- **已验证效果**：删除 ⚠️ 后转码成功（已写自动化：全库扫描保证可 GBK）

## SK-009：Synth 8-2576 —— always 块里给 wire 赋值（必须是 reg）

- **适用场景**：综合报 `[Synth 8-2576] procedural assignment to a non-register xxx is not permitted`，xxx 指向文件某行
- **使用方法**：
  1. 规则铁律：**wire = 连续赋值(assign)，reg = always 块里赋值**。在 `always`（无论时序或组合）里被 `<=`/`=` 赋值的信号，声明必须是 `reg`

  3. 反例高频位置：`always @(*)` 里写 case 查表给 `wire` 赋值（WaveCore 已在 bin2bcd.done、freq_ctrl.preset_fcw 各踩一次）
- **失效条件**：报错信号确实在 always 外还有 assign 驱动 → 属于多驱动问题，不是改 reg 能解决（需重构成单一驱动源）
- **来源**：WaveCore 真实踩坑（2026-09-03 bin2bcd.done；2026-09-04 freq_ctrl.preset_fcw）
- **已验证效果**：改为 reg 后两次均综合通过

## SK-010：迟滞比较（施密特触发）抗阈值抖动——过零计数防重

- **适用场景**：用"幅度越过某阈值就计数"做周期/频率测量时，低频信号每个采样点变化 <1LSB，量化噪声让信号在阈值附近来回跳 → 计数值虚高（实测 37.5kHz 计出 ~1.5 倍）且每帧不稳
- **使用方法**：把单阈值改成双阈值 + 状态：
  1. 信号**跌破低阈值 L**（如 112）→ 进入"武装"
  2. 已武装且**升过高阈值 H**（如 144）→ 计 1 个周期，回到"未武装"
  3. L~H 之间是"死区"，噪声跳不出死区就不会误计
  4. 阈值要放在信号摆幅内（如回环 Vpp 中心 128±67 → 用 112/144 安全），幅值过小会测不到
- **失效条件**：信号幅度比死区还小（Vpp < ~64）→ 永远武装不上/计不到，需改用测周法或动态阈值
- **来源**：WaveCore P0-1 实测踩坑（2026-09-05：任意频率 37.5kHz 测值飘 57600~61000）
- **已验证效果**：加迟滞后稳定在 37500/37600（±1 计数 = ±100Hz = 0.27% <1% 达标）

## SK-011：FPGA 里"除以常数"换成"乘常量 + 右移"

- **适用场景**：需要 fcw = Hz x 2^32 / 50MHz 这类"除以常数"的换算；FPGA 除法器又贵又慢
- **使用方法**：把除法改写为定点乘：除数 c 的倒数放大 2^k 倍取整成整数 M，则 x/c ≈ x*M >> k。
  实例：2^32/5e7 = 85.89934592 → 放大 2^24 取整得 M=1_441_150_920 → fcw = Hz × M >> 24（误差 <0.01%）
- **失效条件**：注意乘积位宽（本例 32b×31b=63b 需声明 64 位中间量）；被除数超范围时先限幅
- **来源**：WaveCore P0-1 设计（2026-09-04）
- **已验证效果**：37.5kHz 实测误差 <1 计数

## SK-012：迟滞阈值必须自适应波形中心（固定阈值会失效）

- **适用场景**：用"幅度阈值+迟滞"做周期计数，Vpp 正常（如 133）但低频段就是数不到周期/只数到一部分；或信号带直流偏置（回环/耦合会把中心从 128 抬走）
- **使用方法**：
  1. 症状特征：高频(≥10kHz 闸门法)正常、低频(测周法)卡死；调 V 正常 → 别只查代码，先怀疑"波形中心漂了"
  2. 修法：每测完一轮，用实测 (max+min)/2 算出**波形中心**，下一轮阈值 = 中心±死区(如±12)，别写死 128
  3. 初值给一个保守默认(中心 128 → 112/144)，一轮后自动收敛
  4. 注意 max+min 可能超 8bit → 用 9 位求和再移位
- **失效条件**：幅度小于死区 2 倍(<~24)时依然无效 → 改用测周法+动态中心或无阈值方法
- **来源**：WaveCore P0-2 真实踩坑（2026-09-05：ev 数到 31 停住=第 32 周期等不到，根因=直流偏置使信号够不到固定低阈值 112）
- **已验证效果**：改后全频段测频达标（P0-2 精确；100Hz±3；后续演化见 SK-017）

## SK-013：超位宽字面量会被截断成 0（看似魔法 bug 的真凶）

- **适用场景**：逻辑看似全对（事件数得顺、计时正常）却永远走进错误分支/永远无效——先怀疑"比较字面量写窄了"
- **使用方法**：
  1. `24'h1_000000` 表示 2^24=16,777,216，需要 **25 位**；写成 24 位时高位被截断 → 值变 **0** → `x < 24'h1_000000` 恒为 `x<0`=假！
  2. 数清楚位数：0x1_000000 有 25 位（bit24 置位），必须写 `25'h1_000000` 或 `25'd16_777_216`
  3. 排查法：把可疑常量打印出来/或换成十进制、检查其二进制位数是否超过声明宽度；对任何 `N'h...` 先心算 `2^(N) > 数值?`
- **失效条件**：数值确实 < 2^N 时不会触发；只有"最高位落在声明宽度之外"才中招
- **来源**：WaveCore P0-2 实测（2026-09-05）：低频一直无效分支，全精度调试发现 t 正常，最终定位 `24'h1_000000` 被截断为 0
- **已验证效果**：改后测周法走通、低频恢复正常（P0-2 全频段达标）

## SK-014：xfft(Block Floating Point)的 m_axis_status 必须常收，否则核心卡死无输出

- **适用场景**：xfft 数据喂进去了(tready 正常、状态机走到等输出)但 m_axis_data 永远不出结果/帧极慢
- **使用方法**：BFP 模式每帧会先在 m_axis_status 通道发一条**状态字(块缩放指数)**；若 `m_axis_status_tready` 拉低不接收，核心会**卡住等状态通道**，数据永不输出 → 把 `m_axis_status_tready` 接 1（收下丢弃），数据即恢复
- **失效条件**：Scaled/Unscaled 模式无此问题；BFP 与 Pipelined Streaming 组合时必现
- **来源**：WaveCore P1 FFT 实测踩坑（2026-09-05：LED 状态探针显示卡在 WAIT=11，拉高 status ready 后帧数恢复增长）
- **已验证效果**：拉高后帧计数持续增长、1kHz 谱峰 bin=20 精确命中

## SK-015：大查找表/大缓存必须走块 RAM，否则撑爆 FDRE/LUT

- **适用场景**：综合/实现报 `DRC UTLZ-1`（FDRE 或 Slice LUTs over-utilized）；原因常见于 4096 深度 reg 数组、几百行 case 查找表被综合成寄存器/分布 LUT
- **使用方法**：
  1. 大缓存（如 4096×8 时域缓冲）：声明加 `(* ram_style = "block" *)`，并且**读、写放两个不同的 always**（同 always 读写易被推断成寄存器阵列，触发 FDRE 超限）
  2. 大查找表（如 1024 点窗/波形表）：不要用组合 case（吃几千 LUT），用 `initial $readmemh("绝对路径.hex", mem)` + `always @(posedge clk) q<=mem[addr]`（最可靠块 ROM）；hex 数据文件放工程 src 并**仓库/工程双份**
  3. case 写在时钟沿内+属性贴 reg 声明(Vivado 可能仍不进 BRAM)——直接 readmemh 最稳
- **失效条件**：BRAM 不够时(如 4096 双缓冲 x2)再考虑 LUTRAM/优化；35t 共 50 块 36Kb
- **来源**：WaveCore P1 实测(2026-09-05)：FDRE 需 77108>65950 → f_ram 改块RAM；LUT 21775>20800 → hann 改 readmemh 块 ROM → 最终 **LUT 19282 / BRAM 7**
- **已验证效果**：改后 DRC 通过并可布线

## SK-016：FPGA 大存储一律用官方 IP(BMG/XPM)，别赌手写数组的推断

- **适用场景**：任何 ≥256 深的存储/缓存；或手写 `reg [w-1:0] mem [0:n]` + `ram_style` 时发现：内容恒零 / 被实现成寄存器阵列 / 综合出分布式 LUT / 资源反复超限
- **使用方法**：直接生成 **Block Memory Generator(blk_mem_gen) 或 xpm_memory** 官方 IP 例化——RAM 必进 BRAM、读时序由你选的选项决定、没有推断玄学
- **失效条件**：无（只是多一次 IP 生成）
- **核心教训**：
  1. 同款写法在模块 A 能推断成 BRAM，换到模块 B 的读写结构就可能失效——**"上一个模块成功了"不是保证**
  2. RAM 映射问题不是 RTL 逻辑 bug，静态读代码查不出来，别反复改 RTL 猜；一步到位用 IP 或先上 ILA 取证
  3. 宁可多花 3 分钟生成 IP，也不要赌 2 小时烧录循环
- **来源**：WaveCore P1 波形缓存排障(2026-09-06)：live 能出、ramp 能出、FFT f_ram 能出，但手写 wram 从 BRAM 到 LUTRAM 到线性化克隆全恒零/超资源，改 BMG IP 后一次通过
- **已验证效果**：BMG IP 版波形缓存正常


## SK-017：测占空比/脉宽用"计窗统计法"，别用"边沿间隔法"

- **适用场景**：FPGA 测占空比、脉宽、平均高电平时间；任何"B级信号+廉价模拟前端"场合
- **使用方法**：
  1. 定"判高阈值"：用窗口内 (max+min)/2 中线；信号噪声大时加"连续2拍确认"去毛刺
  2. 开一个统计窗口(闸门恒定长度, 或低频时用 32 周期测周窗)，累计：高电平时钟数 high_cnt / 窗长 win_cnt / 最长连续高电平 max_run
  3. duty = high_cnt/win_cnt；脉宽 = max_run/50 (50MHz→us)；除法用"减法循环"(≤1000拍)避免再开除法器
- **失效条件**：窗口长度 < 1 个信号周期(此时统计无意义，需拉长窗口)；超低频(<100Hz)建议改用周期法
- **为什么**：
  1. "边沿间隔法"(数上升沿到下降沿的tick)对**单个毛刺零容忍**：一个假边沿毁掉整次测量(实测脉宽恒=1个tick)
  2. 计窗统计对毛刺天然平均，重复性实测 **±0.1%**
  3. 低频路径要先"重置统计窗"再进测周阶段，否则窗口混入10ms粗测段，duty 会低 5%+
- **来源**：WaveCore P0 占空比/脉宽排障(2026-09-16)，前后烧录 10+ 次才定位
- **已验证效果（2026-09-17 终极）**：
  - 方波 1k/100k：D=49.9~50.0%、W=6us/500us、F 精确 ✓
  - **正弦 1k/100k：F 精确、D=049.6~050.0%、W=500us/6us、V=140（与电脑抓图139一致）——正弦全维度毕业 🎓**
- **三层数字抗噪金路径（正弦「×2/乱跳」根治）**：
  1. 阈值穿越 + 重新武装 **均"连续2拍确认"** → 治 ×2 假穿越
  2. 占空比统计判高用 **施密特迟滞** → 毛刺不切碎时段
  3. 测量路径 **5点中值滤波**（9比较器排序网络，Python 20万组验证）→ 清 ≥2拍宽尖刺（V: 201→170→**140** 三步证据）
  4. **窗口级 3窗中值平滑**（D/W/V 输出取最近3个统计窗的中值，F 保持即时）→ 拒绝"偶发坏窗"（现象：V 135↔151 闪烁、紧随 D 掉至 047；修后 D 稳在 050.x）
  - 效果三连：F 稳 → D/W 稳 → V 与 PC 完全对齐
  - **心法：信号毛刺要"在哪测就在哪滤"，滤得越宽（3点→5点），数字侧能修的越多**


## SK-018：上电/烧录后"测量乱跳"是暂态收敛，不是 bug

- **适用场景**：FPGA 测量类系统（测频/占空比/幅度）刚上电或刚烧录后的头几秒，读数乱跳
- **原因（两条叠加）**：
  1. **模拟链路建立**：DA 输出、耦合电容、ADC 偏置网络需要时间进入稳态，头几秒波形质量差
  2. **自适应阈值收敛**：迟滞阈值由上一轮 Vpp 推算（我们实现中 Vpp 初值 255 → 死区取最大 12），前几轮测量在"试探"，交叉点抖动 → F 晃
- **现象特征**：**换成方波立刻稳定**（边沿陡、抗噪最强，一轮就把阈值校准），再切回正弦/三角也准
- **使用方法/建议**：
  1. 演示时：先给方波（或任意强信号）跑 1~2 秒"热身"，再切目标波形——可写进报告当"自适应收敛特性"
  2. 想加速收敛（可选优化）：给阈值/Vpp 初值一个更合理的默认（如 128±20），或首轮用固定阈值
- **失效条件**：如果稳态后仍乱跳 → 不是暂态问题，按正常信号/代码排查
- **来源**：WaveCore 9/16 实测观察（用户提问"为什么刚烧录乱跳"），逐条定位
- **已验证效果**：方波→正弦切换后 F/D/W 全部稳定精确


## SK-019：测频/测占空比出现"方波稳、正弦晃"时，先怀疑模拟回环保真度

- **适用场景**：板上"DA→AD 自环回"测量系统；观察到同一频率下换方波立刻稳定、换正弦/三角就晃
- **数据（WaveCore 实测）**：
  | 波形 | F 稳定性 | 占空比 | 结论 |
  |---|---|---|---|
  | 方波 | 稳（逐字精确）| 49.8~50.0% | 数字生成，边沿陡，免疫模拟失真 |
  | 正弦 1kHz | 稳 | 47~48.5% | 尚可（轻微不对称）|
  | 正弦 ~100kHz | 晃 ±0.5% | 36~41% | 模拟通道对正弦保真度差 → 过零抖动 |
  | 三角 | — | ~31% | 畸变更大 |
- **原因**：方波边沿陡、阈值穿越确定；正弦靠 DA 重构滤波+耦合/偏置网络+AD 输入网络还原，接近模拟带宽边界时谐波/振铃把过零点"推来推去"
- **诊断步骤**：
  1. 同频率切方波对照 → 稳 = 测量逻辑 OK，锅在模拟通道
  2. 抓 0x83 波形图：正弦画出来"歪/削顶/振铃"即为实锤
  3. 检查 DA→AD 连线（⚠️ 本队实际使用 **SMA 线**，接触概率较低——勿轻易归因线材）
  4. 终验用外部信号源从 AD 输入接干净正弦
  5. （数字侧）**阈值穿越 + 重新武装 都要"连续 2 拍确认"**：假穿越(凹坑)被滤除；WaveCore 9/17 实装后，正弦 100k→F=100000 稳定、1k→1000 稳定（此前 ×2/乱跳）
- **判定口径**：这不是硬件"坏了"，是低成本板载模拟通道的**固有保真度限制**；指标宣称以方波为准，正弦标注"受模拟前端限制"
- **来源**：WaveCore 9/16 实测（用户提问"方波稳正弦晃是不是有问题"）
- **后续进展**：以上现象已由**数字三层抗噪+窗口平滑**全面收敛（见 SK-017 金路径与 SK-028 温漂）；本条目保留为"诊断思路"——遇到同类问题先做方波对照


## SK-020：新增"大计算模块"后模拟测量变差？先怀疑开关噪声，再谈静默化

- **适用场景**：FPGA 上同时有"高速大逻辑"（FFT/滤波等，每周期翻转成千上万个触发器）与"模拟采集/测量通道"
- **症状**：新增模块后，原本稳定的模拟测量（尤其低频正弦的频率/占空比）开始乱跳；方波/高频反而正常
- **机理（疑似）**：大逻辑突发运行时电流突变 → 电源/地弹噪声耦合进模拟前端 → 缓斜率信号（正弦）过零点被推来推去
- **排查方法**：
  1. 时间线对照：把"开始不稳"与"新增逻辑上线"对齐（本次完全吻合）
  2. 对照实验：低频正弦/方波/高频三组同条件跑
  3. 把新模块改成**按需运行**（命令触发一次）或**默认静默**，再复测
- **解决范式**：命令触发（如 0x8A）、空闲时钟门控、降低运行频率、必要时物理隔离（模拟/数字电源）
- **要点**：**别让加分模块常驻占用**——默认静默、按需唤醒，是这类"演示型大逻辑"的正确姿势
- **来源**：WaveCore 9/16-17 正弦排障。**修正结论(9/17)**：移除自研FFT后正弦仍出现 ×2/乱跳 → FFT 因果性**存疑**；真正修复来自**数字侧三层抗噪**（2拍确认+施密特+中值滤波）。本条目作为「大逻辑按需静默」良好实践保留


## SK-021：环形缓存的"触发采集"要归零指针；跨块改同一寄存器=双驱动 DRC

- **适用场景**：FPGA 用环形/循环缓存做"从触发点开始的波形抓取"
- **两个坑（都踩过）**：
  1. **语义坑**：触发时若只"等缓存绕圈再读"，读出的起点相位是随机的（缓存里混着触发前数据）→ 必须在触发瞬间**把写指针归零**，再写满一整圈才是"全部触发后数据、首点=触发点"
  2. **DRC 坑**：在状态机里直接写 `wr_idx` 会和采集 always 块形成**多驱动**（Vivado: multi-driven net / MDRV-1）→ 正确姿势是**单写者 + 控制脉冲**：状态机发一个 `fill_rst` 单周期脉冲，指针**始终由采集块独家修改**
- **验证判据**：方波 1kHz 下，上升沿触发→帧前 N 点全高；下降沿→全低；自由模式→随机
- **来源**：WaveCore 触发采集实现与排障（2026-09-16 晚，4 次迭代）
- **已验证效果**：B(上升)/C(下降) 前6点 = 全高/全低 ✓


## SK-022：单趟流式取"双峰"用"双最大值级联"，别用"排除当前主峰近邻"

- **适用场景**：FFT 频谱在数据流(逐 bin)上实时找主峰+第二峰，且不能存整段幅度（省 BRAM/FF）
- **踩过的坑**：候选条件写成"与**当前**主峰相隔>2 的 bin 里取最大"——
  主峰寄存器的更新比判定**晚一拍**，导致**主峰那个 bin 自己会被当成候选存入**，且它幅度最大、之后无人能顶掉；结束时再检查"与主峰相隔>2"自然永远失败 → **第二峰永远不发**（方波谐波场景必现；双音两峰等幅时侥幸正常，掩盖了 bug）
- **正确写法（单趟 top-2 级联）**：

```verilog
if (mag > peak_mag) begin
    if (旧主峰 与 新主峰 相隔>2) begin               // 关键: 相隔>2 才降级
        sec_mag <= peak_mag;  sec_bin <= peak_bin;   // 旧主峰 -> 第二峰
    end
    peak_mag <= mag;          peak_bin <= bin_cnt;   // 新主峰
end
else if (mag > sec_mag &&
         |bin_cnt - peak_bin| > 2) begin             // 常规候选也须相隔>2
    sec_mag <= mag;           sec_bin <= bin_cnt;
end
```

> ⚠️ 第二点极易被忽略：**Hann 窗主瓣旁瓣(±1 bin)幅度可达主峰的 50%**，会"顶掉"真正的次峰（如方波 3 次谐波仅 33%）——所以**"降级"与"候选"两头都必须带"相隔>2"约束**。

  结束时再做"相隔>2 且幅度≥主峰/N"的最终校验收报
- **验证判据**：方波 1kHz → S=1001 + A≈3003（3次谐波）；单音正弦 → 无 A；双音 → A=1099 不受影响
- **来源**：WaveCore 9/17 排障（"拆掉幅度门限仍无 A"两轮定位，最终发现是候选存了主峰自己）
- **已验证效果**：**方波 1kHz → S=1001 + A=3003 稳定**（谐波拆分实证）✅；单音正弦无 A；双音 A=1099 正常；等幅双音 S/A 顺序会互换（属正常）


## SK-023：case 的 default 会同周期"吞掉"块内其他非阻塞赋值（last-write-wins）

- **适用场景**：一个 always 块内既有 `case(state)` 状态机，又有**在 case 之外**根据其他条件更新同一个状态寄存器
- **踩过的坑**：采集结束分支写了 `st <= S_START`，但同一拍 `case(st)` 因缺少对应项走了 `default: st <= S_CAP` —— **同块同变量两次 NBA，后面的赢**，状态被悄悄拉回，**FSM 永远出不了空闲态**
- **症状特征**：计数/采集等外围功能全部正常（写指针在爬），但状态机"从未前进"；且 RTL 仿真若按"理想语义"手写会**通过**，只有真机/正确语义仿真才暴露
- **正确写法**：给每个"会被外部条件更新状态"的源状态**显式加一个空 case**（如 `S_CAP: ;`），或把状态更新统一收进 case 内
- **验证判据**：采集完成后应离开空闲态；加"完成锁存+状态轨迹"探针可一眼看到卡点
- **来源**：WaveCore 自研FFT 9/19 排障（4→7 采集正确、之后全场 0；根因即 default 覆盖）
- **已验证效果**：✅ 2026-09-19 修复后上板，0x8A→SF行正常输出（此前核心从未跑完）


## SK-024：定点FFT 两类隐蔽数值坑——"仿真直算骗过表错"与"实数谱镜像抢峰"

- **坑1（表错仿真过）**：旋转因子表生成时误在每个值后补 0（`[c0,0,c1,0,...]`），硬件只有半数地址是真值；而 Python 金标准用 `math.cos()` **直算**、没走表 → 仿真全绿、硬件全错。**教训：当 RTL 依赖查表时，金标准必须从同一份 hex 文件读表**（本次改用读 hex 后立刻复现峰值=20）
- **坑2（镜像抢峰）**：实数信号 DFT 在 ±f 有等幅双峰；找峰扫描若不限制"正半轴(bin≤511)"，平局可能选中 1024−bin 的镜像 → 1kHz 读成 49kHz。**修法：找峰时满足 `rev10(i) ≤ 511` 才接受**
- **症状**：频谱"稳定但错"（每次一样、数值荒谬），最容易误判为时序/接口问题
- **来源**：WaveCore 自研FFT 9/19（上板首值 4732Hz → 修表+限半边 → 977Hz 对齐）
- **已验证效果**：两坑修复后经 SK-025 收口终验——1kHz→SF=976/S2=1025/S3=2978 与模型逐字一致 ✅
  （口径更新：9/28 修偏移二进制映射、9/30 修矩形窗假峰后，当前正确读数为方波 `SF=976 / S2=2978 / S3=4980`、正弦 `976/0/0`，见 SK-034）

- **（2026-09-30 补）数值模型读 RTL 的查表数据，必须按 RTL 的同一口径解释**：
  `src/tw_cos.hex / tw_sin.hex` 是 **16 位补码**存法（如 `SIN[256]=32769` 实为 -32767），
  RTL 用 `reg signed` 读入；模型若按 unsigned 读，频谱会整个发散但**模型自洽**——
  极难发现。判据：模型与浮点参考/板上读数对不上时，**先查表的符号/位宽口径**，再怀疑算法。
  （实例：`hw_analysis/verify_spectrum_frame.py` 第一版就踩在这里，频谱峰值全乱。）

## SK-025：BRAM 读延迟会让"蝶形对了、找峰错了"——读时序必须全链路对齐；"复现硬件"式模拟是终极判案工具

- **场景**：手写 FSM + 单口 BRAM 的算法核（FFT/滤波/检索），读写分时共用地址口
- **本次实录**：`blk_mem_gen_1` 实为 **2 拍读延迟**。蝶形读加了等待（数据算对），**找峰扫描没加等待** → 峰值全部读到"前一地址" → 1kHz 报 1367Hz（bin28）
- **判案神器**：把硬件异常数字当作"假设变体"去模拟——本次"读 i−1"变体在 1k/2k 两组数据上**逐字复现硬件输出**（[1367,1318,1709] / [2686,3369,8740]），一击定案
- **修复范式**：凡"设地址→取数据"的每一处（蝶形读、找峰扫描、状态回读）都必须按同一延迟等待；等待期地址保持不变，则对 1/2 拍延迟都安全
- **来源**：WaveCore 自研FFT 9/19（复活全链排障终章）
- **已验证效果**：修复后 1kHz→SF=976/S2=1025/S3=2978，与模型逐字一致 ✅
  （口径更新：9/30 修矩形窗假峰后为方波 `976 / 2978 / 4980`、正弦 `976/0/0`，见 SK-034）

## SK-029：`ram_style="block"` 只是"愿望"——大缓存退化成一堆触发器 + 巨型读 mux

- **适用场景**：写了 `(* ram_style = "block" *) reg [w-1:0] mem [0:n]`，综合也过了，
  但资源报告里 **FF / LUT 高得离谱**；或"综合 92% 过了、place 却报 `[DRC UTLZ-1]` 超容"；
  或 BRAM 几乎没用到而 FF 快满
- **使用方法（三步识别，10 分钟定性）**：
  1. **容量对账**：算出 `深度 x 位宽` = N。去分层资源报告里找该实例的 FF 数，
     若 `FF ≈ N + 几十` → 这个数组就是触发器，不是 RAM
  2. **查 BRAM 列**：分层报告里该实例的 `RAMB18/RAMB36` 是不是 **0**？
     是 0 = 没进 BRAM；同时看 `LUTRAMs`，也是 0 → 也不是分布式 RAM
  3. **看 MUX 列**：读一个 N 深数组需要 `N/16 x 2` 个 MUXF7、`N/16` 个 MUXF8
     （7 系列 16:1 mux = 4 LUT6 + 2 MUXF7 + 1 MUXF8，正好一个 slice）。
     实测数值与这个估算对得上，就是实锤
- **修法**：改成教科书 Simple-Dual-Port 模板 ——
  **①写口独立 `always`，不带任何复位；②读口独立 `always`，单条无条件读，去掉异步复位；
  ③地址位宽截到数组深度对应的位宽**
  ```verilog
  // 写口(独立 always, 无复位)
  wire wr_en = (state == S_WR) && wr_tick;
  always @(posedge clk) if (wr_en) mem[wr_addr[AW-1:0]] <= din;

  // 读口(独立 always, 无复位, 单条无条件读)
  wire [AW-1:0] rd_addr = ...;
  always @(posedge clk) if (rd_en) dout <= mem[rd_addr];
  ```
  仍不生效 → 直接上 **Block Memory Generator IP 或 XPM**（见 SK-016）
- **为什么这样改等价**：旧写法 `if (cond) m_q <= mem[addr];` 里 `mem[addr]` 是接到 `m_q` D 端的
  **组合读**，效果 = `m_q(T+1) = mem[addr(T)]`；BRAM 同步读同样是 `doutb(T+1) = mem[addrb(T)]`。
  **读延迟同为 1 拍，时序完全一致**，只是把"组合 mux + 触发器"换成了"块 RAM"
- **失效条件**：
  1. `深度 x 位宽 < 1 个 RAMB18（18Kb）` 时 Vivado 更倾向分布式，此时 `ram_style="distributed"` 更合适
  2. 读写需要**两个以上端口**时，普通 SDP 模板不适用（要真双口 IP）
- **改完怎么确认真的成功了（本次实测的闭环判据，强烈推荐）**：
  **不要用"顶层汇总表里某一行 BRAM 的数量"当判据** —— 那是本次踩的坑。
  - 错的做法：看综合报告 `RAMB18E1` 从 4 变没变成 6。→ **会误判**。
    因为综合阶段 **OOC IP（`xfft_0` / `blk_mem_gen_0/1`）是 Black Box，块 RAM 不计入**，
    那一列本来就会少算；本项目实测 `RAMB18E1` 一直停在 4，而修复其实**完全成功**。
  - 对的做法：**按"实例名 + 原语类型"查**。在 DRC 报告或时序报告里搜实例名：
    ```text
    修复前: Destination: u_fft_demo/f_ram_reg[3025][5]/D  ... SLICE_X4Y63  FDRE
    修复后: The RAMB36E1 u_fft_demo/f_ram_reg has an input control pin ... ADDRARDADDR[10]
    ```
    **同一个实例名，原语类型由 `FDRE` 变成 `RAMB36E1`** —— 这是最难反驳的证据。
  - 辅助判据（本次实测）：`Slice Registers` 35818 → **2443**（正好少掉 32768 个 FDRE），
    `F7/F8 Muxes` 4379/2180 → **11 / 4**（那个 4096:1 mux 消失）。
  - **`4096 x 8 = 32 Kb` 正好塞进一个 36 Kb 的 `RAMB36E1`**，所以一次只多一个 RAMB36，
    不要把"只多了 1 个块"当成"没生效"。
  - 另：**综合报告的 LUT/FF 不含 OOC IP**，只能用于"同一对象前后对比"；
    要判断"布不布得下"，必须看 `impl_1/board_top_utilization_placed.rpt`。
    本项目实测：综合 `3702 / 2443`，实现后 **`5117 / 4834`**。
  - **估收益时别只算读 mux**：一个 4096 深数组退化后，**写口还要给 4096 个触发器各做一份
    地址/使能译码**。按"读 mux ≈ 8192 LUT6"估出 11000~13000，实测只有 **5117**，低估一倍多。
- **核心教训（最值钱的一条）**：
  **`ram_style` 是"建议"不是"保证"，写了不等于进了 BRAM。**
  只要没在资源报告的 **BRAM 列**里看到它，就当它没进。
  而且要"综合 + 实现"两段都看 —— `opt_design` 会为时序做 retarget / 逻辑复制，
  **本项目实测 19231(92.46%) 被推到 20829(100.14%)，"综合过了"完全不代表"布得下"**
- **来源**：WaveCore 2026-09-30 `place_design` 报 `ERROR: [DRC UTLZ-1]`。
  定位到 `fft_demo` 的 `f_ram`（4096x8 = 32768 bit）被综合成 **32768 个 FDRE**，
  外加一个 4096:1 x 8bit 的读 mux（约 8192 LUT6 + 4096 MUXF7 + 2048 MUXF8），
  一个数组吃掉全设计 **86% 的 LUT / 93% 的 FF**。

## SK-031：Windows `.bat` 必须纯 ASCII + CRLF —— "双击黑框一闪就关"的根因

- **适用场景**：给非开发者的"一键脚本"双击后窗口一闪就没了；或脚本好像跑了但什么都没发生；
  或报 `'xx' 不是内部或外部命令`、`xxx 找不到指定的文件`
- **根因**：`cmd.exe` 读 `.bat` 用的是**系统代码页**（中文 Windows = GBK），
  **即使文件是"无 BOM 的 UTF-8"也一样**。于是：
  - 中文被当成 GBK 解码 → 产生**乱码字节**，其中有些正好是 cmd 的**命令分隔符**（`)` `&` `|`）
  - 一旦它们出现在 `if (...)` / `for (...)` 块里或 `set` 语句里 → **括号被提前闭合**、
    命令被劈成两半，后面的行全部变成"不是内部或外部命令"
  - 更阴的是：**脚本会"看起来正常运行"，但关键的 `call` 行被吃掉了** —— 什么都没执行
- **两条硬规矩**：
  1. **纯 ASCII**：文件里不允许出现任何 `ord(c) > 127` 的字符。中文说明放到配套的 `.md` 里
  2. **CRLF 行尾**：LF-only 的文件配合被误解码的字节会进一步错位
- **自检方法**（Python 一行）：
  ```python
  d = open('x.bat','rb').read()
  print('non-ascii =', sorted({c for c in d if c > 127}),
        'lone LF =', d.count(b'\n') - d.count(b'\r\n'))   # 都应为空 / 0
  ```
- **配套设计规矩**（让脚本"自己会说话"，出事不用猜）：
  - **把判据打在窗口上**：成功/失败要各自 `echo` 出可读结论，别只留一行英文报错
  - **每个脚本写自己的 `*_steps.log`**（带时间戳 + 当前进行到第几步）——
    "窗口一闪就关"时，这个文件是唯一能证明"它到底跑没跑"的证据
  - **结尾必须 `pause >nul`**（或 `pause`），否则双击跑完立刻关窗，用户永远看不到结果
  - 错误分支用 `goto noVivado` / `:gotBit` 这类**显式标签**跳转，别用长 `if (...)` 嵌套
  - **整份脚本尽量不让任何一行待在 `( )` 块里** —— 从结构上就免疫括号被劈开
- **附带坑**：`echo ... -> xxx` 里的 `>` 是**重定向**，会在当前目录**生成一个叫 `xxx` 的文件**
  （本项目真的生成过一个名为 `send` 的垃圾文件）。要写箭头就用 `--`
- **来源**：WaveCore 2026-09-30。工程根目录的 `rebuild_bitstream.bat` / `program_device.bat`
  是 UTF-8 + 中文 + LF，**从来没能启动过 Vivado**（`rebuild_bitstream.log` 一直不存在），
  用户点了几次都只看到"黑框一闪"。重写成纯 ASCII + CRLF 后实测正确拉起 Vivado 并打印 banner
- **已验证效果**：把"用户以为是自己点错了"变成"脚本本身坏了"，并顺手修好了整条一键链路

## SK-032：复核校验和 / 审计脚本时，先读生成器源码，别凭直觉写公式

- **适用场景**：要"独立复核"别人（或自己）给的帧、包、CRC；写断言/审计脚本
- **踩过的坑**：把 `SUM = 全部字节和`（`sum(b[:-1])`）当成公式去校验 7 条帧 →
  **7 条全部报 BAD，而且错误值高度一致（一律 +1）**
  - **这种"错得很有规律"就是信号**：一致偏移说明是**公式少了/多了几个字节**，不是数据坏了
  - 本项目真实公式是 `SUM = TYPE + LEN_H + LEN_L + PAYLOAD`，即**跳过 2 字节帧头 `5A A5`**
- **正确姿势**：
  1. **先读生成器源码**（`host/make_frames.py` 的 `s = sum(body) & 0xFF`），确认公式的**起止边界**
  2. 再**跑一遍生成器自证**（`python host/make_frames.py`：本项目输出"全部 20 条已通过自校验"）
  3. 两条都对上了，才拿自己的脚本去复核新帧
- **纪律**：**校验失败先怀疑校验器，不要先怀疑数据**；规律性错误 = 公式问题
- **来源**：WaveCore 2026-09-30，复核 `uart_protocol.md` 里 7 条常用帧的校验和
- **已验证效果**：避免了一次"误把正确的协议文档当成错的去大改"

## SK-033：指标数字一改，必须全库同步（且要区分"当前状态"与"历史记录"）

- **适用场景**：项目里有一个核心指标（资源占用 / 时序余量 / 准确率 / 吞吐……）
  被写进了**十几份文档**（设计报告、答辩稿、演示视频台词、自我介绍、清单、README、
  学习笔记、规划文档）。一旦这个指标变了，文档之间立刻自相矛盾。
- **本项目实测（第 1 次）**：LUT 从 `95.5%` 优化到 `24.6%`、WNS 从 `+1.277ns` 变 `+2.087ns` 后，
  共 **11 份文档 / 16 处**还写着旧数字，其中
  **演示视频台词（要当着评委念）**和 **答辩 Q&A** 最危险。
- **本项目实测（第 2 次，2026-09-30 下午）**：为消除自研通路的矩形窗假峰把 `GAP` 由 `4` 改成 `6`
  后重建，**只有 WNS 一个数字变了**（`+2.087` → `+1.689ns`；LUT 5117 / Reg 4834 / BRAM Tile 10 / DSP 27
  **一个没变**）—— 结果仍然有 **11 份文档 / 16 处**写着旧值。
  ★ 结论：**"只有一个数字变"不等于"改动很小"**。数字进了十几份文档，动一个就要全库搜一遍
  （grep 关键词，再用带断言的脚本替换）。顺带发现根 `README.md` 还停在协议 `v1.15`、
  `WNS≈+3.5ns`、旧谐波数 `S2=1025/S3=2978` —— 说明**同步不能只盯着刚改的那个数字**，
  要顺路扫一眼同一份文档里的其它陈旧值。
- **六条硬规矩**：
  1. **先分类，再改**：
     - **"当前状态类" → 必须改**：设计报告、答辩 Q&A、演示台词、自我介绍、提交清单、README、规划文档
     - **"历史记录类" → 一律不改**：带日期的 session summary / 评审记录 / 协作日志
       （当时数字是对的；改了就是**篡改记录**）
     分不清就问自己："这句话描述的是**现在**，还是**那天**？"
  2. **用带断言的脚本替换，不要肉眼改**：
     ```python
     n = text.count(old)
     assert n == 1, "命中 %d 次, 期望 1 次: %r" % (n, old)   # 命不中就报错, 不静默跳过
     ```
     好处：① 每个文件改了几处一目了然 ② 上游文字被动过时**立刻暴露**而不是悄悄漏改
  3. ★ **替换脚本自己要防“重复命中”（本次踩了）。**
     我要给一句话**追加**一段注解，`old` 用的是那段话的**前缀** ——
     于是**第二次运行脚本时 `old` 仍然命中**，注解被**追加了两遍**
     （`…见下节）（…见下节）`）。
     硬规矩：`old` 必须**连尾部上下文一起带上**，或者落笔前先断言 `new not in text`；
     另外**写文件一律带 `newline=""`**，否则 Python 会按 `os.linesep` 把全文换行整体翻译一遍。
  4. ★ **多行模板 + 单行锚点 = 会悄悄把 LF 塞进 CRLF 文件。**
     脚本为了兼容两种换行，通常准备 `old` / `old.replace("\n","\r\n")` 两个变体。
     但如果 `old` 本身**只有一行**（不含换行），**两个变体都会命中**，脚本会挑中第一个（LF），
     于是"新插入的多行内容"全是裸 LF，而文件其余是 CRLF —— **单文件内换行混用**就这么来的。
     硬规矩：**先判断目标文件的主换行符，再构造 `new`**；或者插入后跑一次全库混用扫描
     （`raw.count(b"\n") - raw.count(b"\r\n") > 0 且 有 CRLF`）收尾。
     ★★ **配套补充（2026-09-30 深夜又踩一次）：光『整文件统一』还不够，得先查清『这个文件该是什么』。**
     本项目同时存在 `.gitattributes`（`* text=auto`）与 `core.autocrlf=true`，结果：
     · git **blob 里是 LF**，工作区**检出来是 CRLF** —— 所以 `git show` 看到的换行 **不等于**磁盘上的换行；
     · 而且**不同目录约定不同**：`src/*.v` 是 CRLF、`report/*.md` 与 `host/*.py` 是 LF、`*.bat` 必须 CRLF（SK-031）。
     ★ **正确做法：以『同一个目录里未被改动过的邻居文件』为基准**，不要凭记忆。
       写完必须用**严格判据**复检：`bad_lf` = 裸 LF 个数（\n 前不是 \r）、`bad_cr` = 裸 CR 个数（\r 后不是 \n），
       两者**不能同时非零**（同时非零 = 真混排）。已固化成常备脚本 `hw_analysis/scan_eol_style.py`（只读、全库扫）。
     ★ 另：**改完 RTL 记得同步工程副本**（仓库 UTF-8 / 工程 GBK），两边解码后要**逐字一致**。
  5. ★★ **"只换行末换行符"的批处理，会在 Markdown 引用块里留下"行内裸 CR"（本次真实报废了一个文件）。**
     本项目的 `board/verify_checklist.md` 原文是**纯 LF**，且大量使用 Markdown 的
     **软换行 + 引用前缀**写法：
     ```
     > 一行正文，末尾两空格
     > 接下一行
     ```
     上一轮的批处理把"行末 LF"换成了 CRLF，结果变成：
     ```
     ...已弃用）\r>   \n> 用途：...
                 ^^^^^^^^ 行内裸 CR: CR 后面跟的是 ">" 而不是 LF
     ```
     **一行里同时含 CR 和 LF**，`b.count(b"\r\n")` 数不到它 → 我上一轮的自检函数
     （只数 CRLF 对）**判它合格** —— 但 `git diff` / 部分编辑器 / Markdown 渲染全被搞乱。
     ★ 硬规矩：**换行自检必须用"逐字节严格判据"，不能只数 CRLF 对数**：
     ```python
     bad_lf = sum(1 for i,c in enumerate(b) if c==0x0A and (i==0 or b[i-1]!=0x0D))
     bad_cr = sum(1 for i,c in enumerate(b) if c==0x0D and (i+1>=len(b) or b[i+1]!=0x0A))
     assert bad_lf == 0 or bad_cr == 0, "单文件内换行混用"
     ```
     我把这个判据写成了常备体检脚本 `hw_analysis/scan_eol_style.py`（只读、全库扫、可直接跑）。
     ★ 附加教训：**遇到这类"文件被自己改坏"时，第一动作是 `git diff` / `git show` 看有没有干净版本可回滚**，
     别急着手写正则去修 —— 本次就是靠 `git show <commit>:<file>` 取回纯净基线才救回来的。
  6. ★★ **正则跨行替换 = 高风险操作，必须先在"小样本 + repr()"上肉眼确认再全量跑。**
     我用 `re.sub(r"\r(>\s*)\n", ...)` 想折叠掉那个裸 CR，结果正则**跨过了行边界**，
     把下一行的 `>` 也吃了进来，生成 `>>` —— **正文被改坏**（幸好有 git 基线可回滚）。
     ★ 硬规矩：批量改写前，先 `print(repr(样本片段))` 看**真实字节**，
     确认"换行到底是 `\n` 还是 `\r\n`、引用前缀长什么样"，
     再决定用"删字符"还是"折叠行"——**两者语义完全不同**。
     ★ 更稳的做法：**先把已正确的换行占位保护起来**（如 `\r\n` → `\x00`），
     处理完剩余裸字符后再还原；处理完必须做一次"**去空白/引用符后逐字比对**"来证明
     只是换行归整、**正文一字未动**（本次校验：8675 个实质字符完全一致）。
- **更隐蔽的一类：语义变了，不只是数字变了。**
  本项目有一处答辩答案在解释"为什么会出现 976/1025 两个相邻 bin"——
  那是**修复前**的行为；修复后该现象已被消除，正确答案变成"正弦 `976/0/0` 单峰"。
  → **纯数字替换救不了它，必须人工重读那段话的意思。**
  另有一处"为什么不做 4096 点"的答案，理由是"资源已 95.5% 满载"——
  优化后这个理由**不成立了**，要改成"当时资源紧张；现在余量 75%，完全放得下"。
- **扫尾**：改完跑一次全库 grep（`grep -rn "<旧数字>" --include=*.md .`），
  确认剩下的命中**全部是"当时/原先"这类历史语境**，而不是漏网。
  再跑一次**乱码检查**（本次就手滑打进过一个 U+FFFD）：
  ```python
  bad = [i+1 for i, l in enumerate(text.split("\n")) if "\ufffd" in l]
  ```
- **来源**：WaveCore 2026-09-30，LUT 攻坚成功后的文档一致性扫尾
  （`hw_analysis/update_stale_resource_numbers.py` 可作为模板）
- **已验证效果**：16 处替换零差错，且**保住了 3 份历史记录的原貌**

## SK-034：FFT / 谱分析仿真别只用"整周期激励"——窗泄漏类问题在仿真里是隐形的

- **适用场景**：给 FFT、加窗、谱峰检测、频率估计这类模块写 testbench；
  尤其当设计里**有窗/无窗**、或用"单位圆打点表"当激励的时候
- **踩过的坑（本项目实测）**：
  - 自研 1024 点 FFT 通路**没有加窗**（矩形窗）。上板跑 1kHz 正弦时读出 `S2=1171Hz`（假峰）。
  - 但仿真 **四个场景全绿**，一个假峰都没报。查 testbench 生成脚本，开头写着：
    > `1024 点 / k 个周期 -> 谱线正好落在第 k 根 bin, 无泄漏。`
  - **原因**：激励是"1024 点正好 k 个整周期"，谱线**精确落在整数 bin**，
    矩形窗在该处的 Dirichlet 核**恰好为 0** → 泄漏=0 → 假峰在仿真里**永远不可能出现**。
  - 真实板子跑 1000Hz 时是 `1000 / (50000/1024) = bin 20.480`，**非整数 bin**，
    泄漏立刻出现：bin24 处 = 主峰 x **13.6%**，刚好越过"主峰/8 = 12.5%"的幅度门限。
- **量化方法（可直接套用）**：矩形窗的 Dirichlet 核
  ```python
  def W(x, N):                     # x = 离整数 bin 的偏移(单位 bin)
      return 1.0 if abs(x) < 1e-9 else abs(math.sin(math.pi*x))/(N*abs(math.sin(math.pi*x/N)))
  # 主峰幅度 = W(frac)；第 k 个合格 bin 的泄漏 = W(k - frac)
  # frac = f/(fs/N) 的小数部分
  ```
  本项目实测（1kHz，谱线落在非整数 bin 20.480；bin24 离主峰 4 个 bin）：
  | 配置 | 该看的那个 bin | 泄漏（占主峰） | 判定 |
  |---|---|---|---|
  | `GAP=4`（09-30 之前） | bin24 | **13.6%**（解析式）/ **14.7%**（离散数值模型） | ❌ 越 12.5% 门限 → 报假峰 |
  | `GAP=6`（09-30 上午） | bin26 | **8.7% / 9.1%** | ✅ 稳定低于门限 |
  | `GAP=4` 或 `6` + **Hann 窗**（09-30 傍晚） | bin24 | **0.9%** | ✅ 余量约 16 倍 |
  ★ **两组数为什么不一样**：`13.6 / 14.3` 是用 Dirichlet 核手算的**解析值**；
  `14.7 / 0.9` 是 `hw_analysis/verify_hann_window.py` 这个**离散数值模型**跑出来的
  （从同一份 `hann_1024.hex` 取窗、同样的 `(s*w)>>7` 整数标度、同样的 L1 模、同样的门限）。
  差 0.4 个点来自 ADC 取整与有限字长 —— **结论方向完全一致，但两套数别混着引用**。
  ★ **两条修法的性质完全不同**（答辩重点，别答错）：
  - `GAP 4→6` 是**"不去看它"** —— 把越线的 bin24 划进保护带，泄漏本身一点没减小；
  - 加 **Hann 窗**才是**"它本来就小"** —— 从 14.7% 压到 0.9%，是真正的根因修复。
- **写 testbench 的正确姿势**：
  1. **至少要有一个"非整数 bin"场景**：让激励频率 = `(k + 0.3~0.5) * fs/N`，
     而不是只测 `k * fs/N`
  2. **最坏相位要覆盖 0.5**（主瓣骑在两 bin 中间，此时泄漏最大）
  3. **要有"加窗 vs 不加窗"的对照**，否则分不清"设计就这样"和"设计有问题"
  4. 检验门限类判据时，**算出门限两边的实际数值再看余量** ——
     本项目 13.6% vs 12.5% 只差 1.1 个点，属于"擦边"，任何微小改动都会让它翻转
- **更强的诊断手法：同信号双通路对照**。本项目两条 FFT 通路同时跑同一路 ADC：
  | 通路 | 加窗 | 1kHz 正弦读数 |
  |---|---|---|
  | IP 通路（带 Hann ROM） | 有 | 只报一个峰 |
  | 自研通路 | 无 | 报出两个峰 |
  **两条通路结论不一致 → 多出来的那个峰是自己造的**。这比单独看一条通路有说服力得多。
- **失效条件**：设计本身就把谱线对齐到整数 bin（如通信里的 OFDM 子载波），
  此时整数 bin 激励是合理的，但**上板/现场的频率通常不是整数倍，仍要补非整数场景**
- **来源**：WaveCore 2026-09-30 新固件首次上板复验
  （2026-09-30 上板实测确认），
  与 SK-025 系列同源 —— 这已是本项目**第二次"仿真通过 ≠ 硬件正确"**
- **根因修复（2026-09-30 傍晚已落地）**：给自研通路**也加上 Hann 窗**——
  复用 IP 通路**同一份** `hann_rom` + `hann_1024.hex`（不新增文件、不动 Vivado 工程），
  `din` 由 `s << 8` 改成 `(s * w) >> 7`。因为 `w` 是 Q15、峰值正好 `32768`，
  **满幅标度一点没变**（±32768），所以蝶形各级的 `>>>1` 防溢出逻辑**一行都不用改**。
  带 `parameter USE_HANN`，改成 `1'b0` 即一键退回矩形窗（09-30 之前的行为）。
- **小改动也要有"数值证据"，不能只靠"看起来对"**：环境跑不了 `xsim`（SK-025），
  于是写了 `hw_analysis/verify_hann_window.py`（纯 Python、不用 numpy 的手写迭代 radix-2 FFT）
  **完全复刻 RTL**：读同一份窗表、同样的整数标度、同样的 L1 模、同样的扫峰+门限。
  ★ 可信性判据不是"结果好看"，而是**它能不能复现已知故障** ——
  该模型在 `GAP=4 + 矩形窗` 下**逐字复现**了板上实测的 `S2=0001171Hz`（bin24），
  这之后它说"Hann 窗后 0/24 报错"才有说服力。
- **已验证效果**：定位到一个"仿真永远抓不到"的结构性假峰，并**落地了可证明安全的最小修复**；
  顺带验证修复**没有副作用** —— 方波真谐波 `976/2978/4980`（bin20/61/102）一根没少，
  满幅范围 `max|(s*w)>>7| = 32512 ≤ 32767` 无溢出

## SK-035：文件“混合编码”——同一个文件里既有 UTF-8 又有 GBK，单编码读必挂

- **适用场景**：中文项目长期“GBK 工程 + UTF-8 仓库”双轨，文件被两套工具/两个编辑器先后保存过；
  尤其那些**你从没细看过的边角文件**（约束、日志、临时表）
- **本次实录**：仓库里的 `board/wavecore.xdc`——一个**第 4 行就白纸黑字写着
  `keep this file ASCII-only (comments in English)`** 的约束文件——实际是混合编码：
  - 第 1 行 `(达芬奇Pro)`、第 14 行 `on 达芬奇Pro,` 是 **UTF-8**
  - 第 50 行 `F1 转发口` 是 **GBK**（字节 `\xd7\xaa\xb7\xa2\xbf\xda`）
  → 后果：任何“假设单一编码”的工具都会挂或显示乱码 ——
  `utf-8` 解码在第 50 行抛 `byte 0xb7` 无法解码；`gbk` 解码则把前两行变成“杈捐姮濂嘝ro”。
  **Vivado 只是把违法的注释丢掉，所以一直没报错 —— 问题被掩盖了很久。**
- **怎么查（逐行试探 + 双编码对照）**：
  ```python
  for i, line in enumerate(raw.split(b'\n'), 1):
      try:
          line.decode('ascii'); continue
      except UnicodeDecodeError:
          pass
      print(i, line.decode('utf-8', 'replace'), '|', line.decode('gbk', 'replace'))
  ```
  只要两列里有一列读出了“像中文的东西”，那一行就是**另一种编码**。
- **修法（优先级从高到低）**：
  1. **让它变成纯 ASCII**（若文件自己就这么要求 —— 本次 XDC 就是）：中文注释直接改英文，
     一劳永逸，也符合“约束文件不该有编码依赖”的常识
  2. 统一成 UTF-8 并去 BOM
  3. 统一成 GBK（仅在工具链强制要求时，如 Vivado 工程里的 `.v` 源码，见 SK-001）
- **顺带一起查的两个邻接问题**：
  - **孤立换行符**：一个 CRLF 文件里混进一行 LF（本次是我自己插新行时带进去的）。
    判据 `raw.count(b'\n') - raw.count(b'\r\n')`，非 0 即混用。
  - **BOM**：`raw[:3] == b'\xef\xbb\xbf'`。`.md` 里无害，
    但 `.py` / `.bat` / `.tcl` 带 BOM 会直接执行失败（`cmd` 尤其认死 BOM）。
- **来源**：WaveCore 2026-09-30 文档一致性扫尾（`hw_analysis/fix_xdc_encoding_and_eol.py`）

## SK-038：Verilog 的"中间量位宽溢出"——读数看起来正常，其实是错的

- **适用场景**：任何"把整数往物理量换算"的地方：频率 = `bin × fs / N`、电压 = `lsb × KN / 1024`、
  时间 = `cnt × 周期`。这类式子**乘法结果常常比你想的宽**，而 Verilog 默认**不报错**。

- **本项目实测（2026-09-30 深夜，一次真实的静默错误）**：
  ```verilog
  // self_fft_1024.v（自研通路，N=1024，Δf=48.8Hz）
  res_freq <= (pk_bin*24'd50000)>>10;
  // fft_demo.v（IP 通路，N=4096，Δf=12.2Hz）
  fft_hz   <= ((peak_bin * 16'd50000) + 12'd2048) >> 12;
  ```
  看着"我已经写了 24 位 / 我写的是 16 位"，**实际都不是**。按 IEEE 1364-2005
  §5.4.1/§5.4.2：
  · 乘法 `i*j` 的自定位宽 = `max(L(i), L(j))`
  · **但赋值语句里右式是"上下文相关表达式"，会被提升到左值(LHS)的位宽**
  · 所以真正生效的位宽 = `max(左值位宽, 各操作数位宽)`

  | 位置 | 我"以为"的位宽 | **实际生效** | 上限 | 正确需要 | 溢出起点 |
  |---|---|---|---|---|---|
  | 自研通路 | 24 | **24**（左值也 24） | 16,777,215 | 511×50000 = 25,550,000 | **bin ≥ 336（16406 Hz）** |
  | IP 通路 | 16 | **24**（被左值提升） | 16,777,215 | 4095×50000 = 204,750,000 | **bin ≥ 336（4102 Hz）** |

- **为什么它特别危险（三条，缺一条都不至于这么难发现）**：
  1. **症状是"看起来正常的错数"**：截断丢掉的是 `2^24`，再 `>>10` 之后**恰好偏 −16384 Hz**。
     不报错、不置 X、不乱跳 —— 屏幕上就是一个"像个频率"的数字。
     ```
     bin 335 -> 16357 Hz  ✔
     bin 336 ->    22 Hz  ✘（正确 16406）
     bin 511 ->  8567 Hz  ✘（正确 24951）
     ```
  2. **既有测试全都不覆盖**：之前所有上板测试都在 1kHz 附近（自研 bin20 / IP bin82）、
     方波 3 次谐波 3kHz（IP bin246）、扫频 800~1200Hz —— **全部低于 4102Hz**。
     ★ 这是 **SK-034 的同一条道理**："测试覆盖不到的地方，等于没测"。
  3. **旁边有个"看起来很准"的模块掩护它**：`freq_meter`（纯边沿计数）在 100Hz~1MHz 都准，
     于是"频率测得准"这个印象掩盖了"频谱读数在 4kHz 以上全错"。

- **怎么发现它的（可复用的排查手法）**：
  1. **可疑特征**：凡是手写了 `N'd<常数>` 的**乘法**，都先问一句"这个位宽够吗"。
     快速判据：`最大操作数 × 常数 > 2^位宽` 就是溢出。
  2. **让"数据模型"去和板上实测对齐**：我写了 `hw_analysis/check_self_fft_overflow.py`，
     把 Verilog 的位宽规则**逐点模拟**出来。它算出的
     `IP 1kHz → 1001`、`自研 1kHz → 976` **与板上实测逐字吻合** ——
     **模型对得上，才有资格用它去判断那 4095 个我没法上板逐一试的 bin**。
     （和 SK-034 的"先复现故障再验证修复"是同一套方法论）
  3. **全 bin 扫描量化影响面**：IP 通路 **3760/4095 个 bin 是错的**、
     自研通路 **176/511 个 bin 是错的** —— 看到这个比例就知道它非修不可。

- **修复**：乘数与加数整体加宽（24 → 32）。代价 = 乘法器变宽，各占 1 个 DSP。
  ```verilog
  res_freq <= (pk_bin*32'd50000)>>10;
  fft_hz   <= ((peak_bin * 32'd50000) + 32'd2048) >> 12;
  ```

- **★ 设计变 fs（时基档位）时，这个坑会成倍放大。**
  `f = bin × FS_HZ / N`：bin 最大 4095（12 位）、FS_HZ 最大 25e6（25 位）
  → 乘积最大 4095×25,000,000 = **102,375,000,000，需要 37 位**。
  **中间量必须给 40 位**，给 24 或 32 都会在某个档位静默溢出。
  更稳的做法：**别在 RTL 里现算 `bin × fs`**，而是改成
  `f = bin × K >> S`（K = `fs/N` 预先算好并做 Q 定标），把位宽控制在可核算的范围内。

- **硬规矩（三条）**：
  1. 写"整数 → 物理量"的换算时，**先把最大可能值算出来，再定位宽**；
     或者干脆**统一给 40 位**（资源代价远小于排查一次静默错误的代价）。
  2. **必须有覆盖"极端值"的测试**：取**最大 bin / 最大 fs / 最大 KN** 各跑一次。
     本项目的补救 = 新增回归场景 F（`sin400.hex`，bin 400），
     **修复前它会报 3147Hz、修复后报 19531Hz** —— 一个真正抓得到 bug 的测试。
  3. **换算值要和"另一条独立通路"对齐**：本项目 IP 通路（4096 点）与自研通路（1024 点）
     互相印证，是这次能这么快定位的关键。

- **来源**：WaveCore 2026-09-30 深夜（复查代码时发现）
- **工具**：`hw_analysis/check_self_fft_overflow.py`（逐点模拟 + 影响面统计）、
  `hw_analysis/verify_freq_conv_fix2.py`（修复前后对照 + 与板上实测对齐）
- **已验证效果**：全 bin 扫描下两条通路 **0 错**；`xvlog`/`xelab` 通过；
  并把"高 bin"补成永久回归场景（`PASS=6 FAIL=0`）

## SK-039 · L1 模是**相位敏感**的 —— 别拿它当"复模"定金标准

- **现象**：自研 FFT 的幅度谱逐字节金标准长期对不上（`y[20]` 实测 207、金标准 200，
  偏 **+7 个码 ≈ 1.28×**），而复现模型（`hw_analysis/verify_spectrum_frame.py`）坚持给 200。
  两者都说自己"整数级复刻"，谁也不服谁。

- **排查路径（值得复用的顺序）**：
  1. **先排口径**：模型与仿真激励的幅度参数是否一致？（本项目：`MID,AMP,HI,LO=128,99,228,28`，一致 → 排除）
  2. **再排表**：窗表 / 旋转因子表，**仓库 `src/` 与 Vivado 工程 `D:/...` 两份是否一致**？
     （本项目三张表都一致；注意仿真脚本原来只校验 hann，**漏了 tw_cos/tw_sin**）
  3. **换一种读法取数**：原来用层次化引用直读 `u_dut.u_mem.mem[k]`，
     结果读到的是**新一轮采集已写入的加窗原始样点**而不是 FFT 结果
     （实测 4137，而同一时刻正弦 n=160 的加窗样点算出来正是 −4140）。
     → 改成**镜像每一笔蝶形写、在进入 S_PEAK 的那一拍整体快照**，与读内存的时机彻底解耦。
  4. **看复模，不要只看标量**：拿到 `re/im` 后一算，
     `√(2133²+5968²) = 6337.5` —— **与理论值一字不差**。
     **复模是对的，是 L1 不对。**

- **根因**：`spec_compress` 吃的是 **L1 模 `|re|+|im|`**（为了省资源，避开开方）。
  而 **L1 随相位变化**：对同一个复模，数学上恒有
  `|X| ≤ L1 ≤ √2·|X|`，换成对数码就是**最多 8 个码的上浮**（`16·log2(√2)`）。
  仿真里激励表自由运行、采集起点任意 → 相位任意 → L1 在区间内取任意值。
  **原来的"金标准"隐含假设了 相位=0 且 L1=|X|，这个假设本身就不成立。**

- **修复**：把幅度判据的上界从 `exp+tol` 改为 **`exp+8`**，
  并注明这是**由 L1 定义推出的数学上界**，不是照抄实测值来"修绿"。
  结果：`PASS=22 FAIL=0`（原 `PASS=7 FAIL=10`）。

- **★ 顺带暴露的产品级事实**：频谱显示的幅度是 **L1 口径，对信号相位敏感**，
  最大可偏离真值 **+3dB**。频谱形状不受影响，但**绝对幅度精度**这一项必须按此口径表述，
  不能宣称"幅度即 |X|"。**这条要写进技术文档的指标口径说明。**

- **来源**：WaveCore 2026-10-16（做自适应窗时被逐字节金标准卡住，顺藤摸瓜查出）
- **工具**：`sim/fft_check/tb_self_fft.v`（新增 `fsnap` 镜像 + `[镜像]`/`[诊断]` 打印）

## SK-041 · 综合日志里的 `CRITICAL WARNING` 必须当错误看，尤其是 multi-driven

## SK-043 · "让位"要区分读操作和写操作 —— 让错了会自锁

- **背景**：`S_PLAY`（回放态）原本只对 `inv_pend`（反向变换请求）让位，
  因为反向变换只在空闲态才能启动。后来"顺手"让 `run_l`（采集请求）也让位，
  理由是"同一类问题"。**这一步造成了死锁。**
- **死锁链条**：
  1. 回放开 → DAC 由 `da_play` 驱动，DDS 不再上 DAC
  2. `run_l` 到 → 退出回放去做采集
  3. 但此刻 AD 收到的是**回放的输出**（可能是 0）
  4. 采到全 0 → FFT 全 0 → mem 全 0
  5. 回放读 mem = 0 → 输出中值 → 步骤 1
- **而且 GUI 的频谱页会周期性反复发 `0x8E`** → mem 每秒被刷成 0 好几次，
  DA 永远出不来。
- **规矩**：
  - **复用已有数据的请求**（0x92 反向变换）→ 可以让位 ✓
  - **会摧毁数据的请求**（0x8A/0x8E 采集）→ **绝不能让位**，必须先关回放 ✗
- **来源**：WaveCore 2026-10-17（IFFT 回放"什么都没有"的真凶之一）

## SK-044 · 加窗 → 处理 → 反变换，窗会变成信号的**包络**

- **数学事实**：`IFFT(加窗信号的频谱) = 原信号 × 窗函数`
- **现象**：IFFT 回放出来的 977Hz 正弦幅度不是恒定的，两端衰减、中间最大（纺锤形）。
  频率计在包络塌陷处漏掉过零点 → 整帧平均后读成 **758Hz**；
  波形识别看到非等幅正弦 → 判成"其他"（TY=3）。
- **这不是 bug**，是加窗重建的固有性质。用户看到的两个"读数异常"是同一个原因。
- **试过但失败的修复**：按 `1/max(hann,0.25)` 做逆窗查表补偿（增益 1~4 倍）。
  实测**反而更差**：
  ```
  mem 各段峰峰值:      17 15 22 31 28 36 30 20 20 14
  逆窗补偿后 da_play:  50 52 52 50 48 16 16 48 52 52   ← 第5/6段塌陷
  ```
  根因：帧内含约 14% 量化杂散，**真实包络不严格等于窗函数**，
  理想逆表在"包络本已偏大"的地方**过度校正**。
- **正确路线**（若以后要做）：
  1. 重建通路改用**矩形窗**（但本设计正向通路会溢出，需先解决位宽）
  2. 对**窗谱**做逆滤波（不是对时域做）
- **规矩**：做"频域滤波 + 反变换"这类功能，**选窗要按重建需求选，不是按分析需求选**。
- **来源**：WaveCore 2026-10-17

## SK-045 · 位反转存储的引擎，回放读地址必须先确认顺序 —— 而"确认"要用频谱，不是肉眼

- **背景**：本引擎是"自然序输入、位反转存储输出"。回放时该读 `mem[n]` 还是
  `mem[rev10(n)]`？
- **走过的弯路**：先后改了两遍方向，两次都"看起来有理由"：
  - 第一次看到波形剧烈交替 → 判断要位反转
  - 第二次拟合发现自然序解释 42% 方差、位反转 0% → 判断不要位反转
- **真实原因**：**dump 采样与 `play_idx` 不同步**。
  采样率是变化率的 8 倍 → 采到大量重复点 → 频谱被"零阶保持"污染成 2 的幂次 bin
  （bin 64/128/256）→ **看起来完全像位反转数据**。
- **正确判据**（一次定死）：**取整一圈，对读出的序列做 FFT，看主峰 bin 的能量占比**
  ```
  顺序读 mem:   bin20 占 56.1%   ✓
  位反转读:     bin20 占  0.0%   ✗
  ```
- **规矩**：
  1. dump 硬件波形时，**采样要对齐到数据真正更新的节拍**（`play_idx` 变化沿），
     不能用 `repeat(N)` 估
  2. 判断顺序/乱序，**看频域能量占比**，不看时域长相

## SK-049 · "两条通路并行"要配一个来源切换开关，否则对照叙事立不住

- **背景**：本项目有两条波形识别通路（规则法 TY / 神经网络），
  两条一直在跑，但对外只报一路（规则法）。
- **问题**：这样"同一功能两种实现"的对照**没法当场演示**——
  评委/用户看不到另一路的结果，只能听口头描述。
- **解法**：加一条切换命令（`0x96`），决定 `TY=` 行用哪一路；两条通路**始终运行**，
  切换只改变"报哪一路"，不改变行为。**默认值保持原状**（规则法），与升级前完全兼容。
- **关键细节：编码要统一**。两条通路原生的类别编码不同

  上位机无需区分。否则切换后读数会"莫名其妙地颠倒"。
- **附带好处**：`0x95`（直读神经网络结果）**不受 `0x96` 影响**，
  所以对比时两路可以同时观测。
- **来源**：WaveCore 2026-10-17

## SK-050 · 定点量化的两个隐形坑：偏置没跟着缩放 + 用错位宽做约束

- **背景**：两层 MLP（6→16→4），浮点 99.8%，定点只有 89.5%，
  且"其他"类掉到 61% 而前三类都是 99% —— **这种不均衡不是均匀舍入误差**，值得查。
- **坑一：输出层偏置没跟着缩放**。
  隐层按 `hq = h·Q/H_MAX` 归一化（H_MAX 是隐层激活最大值，本例 4.55），
  于是 `hq@W2q` 这一项天然带着 `1/H_MAX` 因子；但偏置按 `b2·Q` 量化，**没有这个因子**。
  结果：**偏置被相对放大了 H_MAX 倍**，判决被系统性推向样本最多的类别。
  症状就是"多数类几乎全对、少数类被吞掉"。
- **坑二：层间移位用公式取整**。
  原写法 `SH2 = round(log2(S2))`，一是没计入 H_MAX，二是 log2 后取整误差可达 40%。
  而 SH1/SH2 本来只有离散几档，**不如直接在验证集上搜**。
  评分用「先总准确率、再最差一类」，避免选出"三类完美、一类崩"的参数。
- **坑三（自查时犯的）**：我一开始按 **int32 的 2.15e9** 给累加器设上限，
  但 RTL 用的是 **40 位**（±5.5e11）—— 把**软件模拟的位宽当成硬件位宽**，
  白白排除了更优参数。
  **规矩：做量化约束前，先确认 RTL 的实际位宽，别拿 numpy 的默认类型想当然。**
- **配套**：权重或移位一改，**测试向量必须重新生成**（`gen_nn_vectors.py`），
  否则会出现"RTL 与模型不一致"的假失败（实测 PASS=61 FAIL=3，其实是向量过期）。
- **结果**：89.5% → 91.3%，"其他"类 61.3% → 86.7%（前三类各让 3~8 点，

## SK-054 · 对"对数码"取平均是错的 —— 平均必须在压缩之前

- **背景**：做幅度谱 N 帧平均降底噪。链路是
  `17 位线性幅度 -> spec_compress(8 位对数码) -> spec_buf -> 串口`。
- **错误做法**：在 8 位对数码上累加平均。
  对数是**非线性**的，`mean(log(x)) ≠ log(mean(x))`——
  得到的既不是平均幅度，也不是平均 dB，物理意义不明；而且底噪**不会**按 sqrt(N) 下降。
- **正确做法**：在 `spec_compress` **之前**、17 位线性域做平均。
- **工程细节**：接进去之后，下游的打拍级数要对齐 —— 平均器有 3 拍延迟，
  写缓存的**使能和地址都要延迟同样的拍数**，否则数据与 bin 号错位
  （现象：谱整体错位一格或几格，看起来"像"另一次 FFT 的结果）。
- **来源**：WaveCore 2026-10-18

## SK-055 · 带累加器的模块，三个必查项

做 `spec_avg`（滑动平均累加器）时，三个 bug 全是这类模块的共性问题，
而且**都是仿真给出来的、不是看代码看出来的**：

1. **BRAM 上电是 X**。第一次读出的 `q` 是 X，`q - q/N + x` 全是 X，且会一直传播。
   现象：输出恒为 `x`（不是 0，也不是某个错值，就是 `x`）。
   修法：`initial for (i=0;i<512;i=i+1) mem[i]=0;` —— Vivado 会写成 BRAM 的 INIT，不占逻辑。
   **试过"给每个 bin 配 valid 标志位"，但标志位本身也是 X，问题照旧。**
2. **流水线的三级必须对齐到同一个地址**。
   错误写法：`q <= mem[addr]`（当拍）与 `mag_1`（上一拍）直接相减 ——
   把 A 位的旧累加加到 B 位的新样本上。现象：收敛值不对、误差随数据而变。
   正确写法：`nsum` 先打一拍，写回时用的地址也再延一拍。
3. **测试台不能用"背靠背压同一个地址"**。
   真实场景每帧顺序扫 512 个 bin，同一 bin 隔 512 拍才再访；
   而流水线有 3 拍延迟，背靠背压同地址会读到旧值、累加漏拍。
   现象：收敛值偏小、且收敛变慢 —— 很容易误判成 RTL 错。

- **附带**：滑动平均要减 `acc/N` 才是"滑动"。不减就是无限累积，
  信号变化时输出跟不上（表现为"黏住"旧值）。
- **来源**：WaveCore 2026-10-18

## SK-057 · "一块存储器，两种含义" —— 回放前必须确认里面装的是什么

- **现象**：IFFT 演示时示波器上是**一片密集尖刺**（真毛刺，探头确实接好了）。
- **根因**：`mem` 装了两种完全不同的东西，而回放不区分：
  | 时刻 | mem 内容 | 开回放看到 |
  |---|---|---|
  | `0x8A` 之后 | **频域数据** | 剧烈跳变的尖刺 |
  | `0x92` 之后 | **时域波形** | 正常波形 |
  用户少发了 `0x92`（或者 GUI 压根没帮着发），回放就把**频谱当波形放**——
  相邻点数值乱跳，示波器上就是"一堆毛刺"。

  这是可见的、可接受的诊断行为"。上一轮调试为了排除 `inv_done`，**主动去掉了这个门**，
  于是这个"可接受的诊断行为"变成了**默认行为**。
- **修法**：
  1. 加 `play_valid` 标志 —— 正向采集时清零、反向变换完成时置 1；
     回放时若 `play_valid=0` 则**输出中值（静音）**，而不是放垃圾。
     **静音是"明确地告诉用户还没准备好"，垃圾是"误导"。**
  2. GUI 的「运行滤波」改成**一键三步**：`0x8A` → 等 400ms → `0x92`，
     并在状态栏显示 `1/3 → 2/3 → 3/3`。
- **规矩**：**任何"读共享存储器"的功能，都要有一个"内容有效"标志**，

## SK-068 · 用 xvlog 严格模式能抓出 Vivado 综合放过的一类隐患

- **现象**：`xvlog` 编译整个 `src/` 直接报 15 个 ERROR：
  ```
  ERROR: [VRFC 10-2938] 'nf_f0' is already implicitly declared on line 160
  ERROR: [VRFC 10-3380] identifier 'st' is used before its declaration
  ```
  全是「信号在声明之前就被使用」。而 Vivado **综合一直是过的**、板子也一直正常。
- **根因**：Verilog-2001 规定，未声明的标识符会被**隐式声明成 1 位 wire**。
  Vivado 综合器足够宽容，遇到后面的显式声明会采取后者，所以实测行为正确。
  但这是**依赖工具宽容度**，不是设计保证。换成 Quartus / Efinity / yosys 就可能真按 1 位处理。
- **危害取决于位宽**：
  | 信号 | 本意 | 被截成 1 位的后果 |
  |---|---|---|
  | `st`（freq_meter） | 3 位状态 | 状态机只剩 2 个状态 |
  | `max_v`/`min_v` | 8 位样点 | Vpp 直接算错 |
  | `win_out`（fft_demo） | 16 位样点 | FFT 输入只剩 1 比特有效 |
  | `nn_cls` | 2 位类别 | 神经网络 4 类退化成 2 类 |
- **修法**：声明前置、赋值留在原处。
  - `wire signed [15:0] win_out = prod[30:15];`（在后）
    → 前面写 `wire signed [15:0] win_out;`，原处写 `assign win_out = prod[30:15];`
  - `reg` 直接搬声明行即可。
  **不要**把声明整体挪到文件头了事 —— 那会打乱原有的分组注释。
- **怎么做**：`xvlog -sv src/*.v` 一条命令，30 秒跑完。**每次改完 RTL 都跑一遍**，
  比等综合（15 分钟）快得多，而且它能抓到的这类问题综合器根本不报。
- **来源**：WaveCore 2026-10-19

## SK-070 · 位宽不够时，常量会静默截断成 0，整个状态分支变成死代码

- **现象**：`self_fft_report.v` 里 WIN= 行**从上板第一天起就一次也没发出去过**。
  实测串口：`SF=0000999Hz | S2=... | S3=... | F=0001000Hz` —— S3 之后直接接测量行，没有 WIN。
  但源码里明明写了 `state <= S_WINS` 和完整的 `S_WINS` 分支。
- **根因**：
  ```verilog
  localparam S_WAIT=2'd0, S_CF=2'd1, S_WF=2'd2, S_SEND=2'd3, S_WINS=2'd4;
  reg [1:0] state;      // ← 2 位只能装 0~3
  ```

  前者排在前面，**`S_WINS` 分支永远匹配不到**。
- **为什么没被发现**：综合器不报错、不警告（重复 case 项在 Verilog 里合法，取第一个）。

- **排查方法**（一条命令扫全库）：
  正则找 `\w+\s*=\s*(\d+)'d(\d+)`，若 `值 >= 2^位宽` 就是同类问题。
  ```python
  for m in re.finditer(r"(\w+)\s*=\s*(\d+)'d(\d+)", code):
      if int(m.group(3)) >= (1 << int(m.group(2))): 报告
  ```
- **修法**：`state` 加宽到 3 位，常量改 `3'dN`。
- **教训**：**加状态时先看 state 的位宽**。加第 5 个状态（2 位装不下）是最容易踩的点。

## SK-074 · 带宽不够先怀疑抽取，别急着上等效采样

- **现象**：文档里写着"观察带宽 25kHz"，第一反应是 ADC 太慢，
  于是去研究等效采样（ETS）。**这个判断是错的。**
- **事实**：ADC 一直是 25MSPS，Nyquist 是 **12.5MHz**。
  25kHz 是 DSP 侧 `decim=1000` 抽出来的，`timebase.v` 注释自己写着
  「decim 下限受 ADC 限制(25MSPS -> 最小 2)」。
- **规则**：**先问"限制来自采样还是来自抽取"，再决定用不用 ETS。**
  ```
  要看的频率 f  <  fs_ADC/2   ->  减小 decim 就够了，不需要 ETS
  要看的频率 f  >= fs_ADC/2   ->  才轮到 ETS（或换更快的 ADC）
  ```
  本项目：f ≤ 12.5MHz 都属第一种；**1~5MHz 直接开原始采样即可**。

- **等效采样（ETS）真正的适用条件**（只在第二种情况用）：
  1. 信号**必须是周期的**（ETS 靠多次采集拼一个周期，非周期信号没法拼）；
  2. 需要一个稳定的触发，并且能在**亚采样间隔**上步进相位；
  3. 触发抖动直接决定重建质量 —— **先测抖动，再决定做不做**；
  4. 本质是"用时间换采样率"，代价是采集时间变长、且不能看瞬态。
- **反例提醒**：如果信号频率与采样率成整数比，ETS 的相位永远落在同样的点上，
  一点信息都补不出来 —— 必须让 f 与 fs 满足**非整数关系**（相位慢走）。
- **本项目有利条件**：DDS 与 ADC 同源 50MHz 时钟，相位关系是确定的，
  一旦要做 ETS，相位步进可精确控制，不受时钟漂移影响。
- **来源**：WaveCore 2026-10-23（被"25kHz 就是 ADC 上限"误导了一轮）


## SK-075 · 拼接是无符号的，会悄悄把负数变成大正数

- **现象**：噪声发生器输出波形被削掉一半，Vpp 从 4868mV 掉到 2506mV，
  锁相幅度崩掉 86%。语法没错、综合无警告、仿真也看不出来。
- **根因**：
  ```verilog
  wire signed [9:0] sum = sig1 + {{2{noise2[7]}}, noise2};   // ← 错
  ```
  `{a, b}` 拼接的结果**是无符号的**。只要表达式里有一个无符号操作数，
  **整个加法就按无符号算**：负的 `sig1` 被**零扩展**成大正数，撞上上饱和。
- **正确写法**：两边都先变成有符号再相加
  ```verilog
  wire signed [9:0]  nz  = $signed({{2{noise2[7]}}, noise2});
  wire signed [10:0] sum = $signed(sig1) + nz;
  ```
- **规则**：**凡是把拼接结果和有符号数混在一起运算，一律先 `$signed()`。**
  自检办法：拿一个负输入跑仿真，看结果是不是变成了接近最大值。
- **同类陷阱**：`a + b` 的结果位宽 = max(位宽)+1，但**符号性**取决于最低位的操作数；

## SK-076 · 超时退出必须同时撤掉请求，否则是活锁不是恢复

- **现象**：给一个"等条件"的状态机加看门狗，超时回 IDLE。加了之后**现象和没加之前一模一样**，
  还是会挂。区别只是板子不再整机静默。
- **根因**：`wav_hold = req_l`，超时只清了状态、**没清 req_l**。
  回到 IDLE 后 `req_l` 还是 1 → 立刻重进 HOLD → 再次超时 → **无限循环**。
  从外面看就是"卡住了"，和原来的死锁无法区分。
- **规则**：**超时/异常退出的那一条路径，必须把触发这次操作的所有标志一起复位。**
  ```
  if (超时) begin
      req_l <= 0;      // ← 少了这一句，看门狗等于没加
      busy  <= 0;
      st    <= IDLE;
  end
  ```
- **自查**：加完超时后，问一句"退出之后，下一秒会不会又立刻进来？"
  会，就是没退干净。
- **顺带**：看门狗要覆盖**所有非空闲状态**，不能只覆盖想得到的那两个。
  实测卡在发送态（HEAD/PAY），只给 HOLD/FILL 加超时完全没用。
- **来源**：WaveCore 2026-10-23（波形帧 T3 事故）


## SK-077 · 验收判据要按物理分辨率定，不能拍脑袋写百分比

- **现象**：回归脚本里写"谱峰频率误差 < 1%"，T1 档 1kHz 永远不过，
  读回 977Hz（2.34%）。
- **真相**：**硬件是对的，判据是错的**。T1 的 Δf = 48.83Hz，
  谱峰只能落在整数 bin 上，1kHz 落在 bin 20（976.6Hz）和 21 之间 ——
  **半个 bin 就是 2.4%**，判据 1% 永远不可能满足。
- **规则**：**任何"量化过"的量，容差必须先算物理分辨率，再乘一个合理的 bin 数。**
  ```
  错误：  |f_measured - f_true| / f_true < 1%
  正确：  |f_measured - f_true| <= Δf / 2      （半 bin）
          或 <= Δf * N                        （允许 N 个 bin 的误差）
  ```
- **同类**：频率测量 ±1 计数、ADC 量化 ±0.5 LSB、时间测量 ±1 采样周期 ——
  都属"先算分辨率再定容差"。

- **来源**：WaveCore 2026-10-23（回归首轮 5 项失败，2 项是测试自己的错）

## SK-080 · 计数器饱和点如果落在判据窗口外，就是一颗定时炸弹

- **现象**：IP FFT 的 `S=`/`A=` 停发，切档也不恢复。看着像"卡死"。
- **根因**（一行代码）：
  ```verilog
  wire window_ok = !meas_busy && (idle_cnt >= 3000) && (idle_cnt <= 350_000);
  ...
  else if (idle_cnt < 400_000) idle_cnt <= idle_cnt + 1;   // ← 饱和在 400000
  ```
  **饱和点 400000 在窗口上限 350000 之外。** 计数一旦跑过 350000，
  就再也回不到窗口里——除非有别的东西把它清零。
  这里靠 `meas_busy`（每 42ms 一次）清零，**那东西一停，窗口就永久关闭**。
- **规则**：**写「区间判据 + 饱和计数器」时，先问饱和点落在哪。**
  ```
  错误：饱和在窗口外   -> 冲出去就回不来，永久失效
  正确：饱和在窗口内   -> 最坏情况也会停在"发得出去"的状态
  或者：到点绕回       -> 周期性重开，不会永久锁死
  ```
- **更一般的形态**：任何"等某个外部信号来复位"的计数器，都要问
  **"如果那个信号永远不来，会怎样？"** 答案不能是"永久失效"。
- **验证手段**：把内部量引出来读（这里是新增 0x9E），
  一次读出 `idle=399872, win=0` 就直接定位了，比读十遍代码快。
- **反面教训**：修的时候试过"把窗口开到常开"，锁死是没有了，
  但 `S=` 开始抢占测量行，回归出现 3~5 项**随机**失败。
  **用"经常出错"换"偶尔卡死"是错的**，尤其对测量仪器。最终选了"周期性窄开"。
- **来源**：WaveCore 2026-10-24（IP FFT 停发，已修复）

## SK-082 · 生成 .bat 时把转义符写多了 —— 17 个一键脚本有一半点不开

- **现象**：双击 `run_xxx.bat`，窗口一闪就报
  ```
  系统找不到指定的路径。
  [ERROR] Python 3.8 not found.
  ```
  但 Python 明明装着，路径也确实是那个。
- **根因**：用 Python 生成 .bat 时，把**给格式化字符串用的转义**直接写进了文件：
  ```python
  content = '''
  cd /d %%~dp0
  set PY=C:////Users////Lenovo////...////python.exe
  if not exist "%%PY%%" goto nopy
  "%%PY%%" -u foo.py %%~1
  '''
  ```
  - `%%` 是**格式化时**才需要双写的；直接写文件应该用单个 `%`
  - `\\\\` 在普通字符串里是 `\\` 两个，写进文件就是四斜杠 `C://Users//`
  - 结果：`cd /d %%~dp0` 展开成 `%` + 提示符路径，`set PY` 设成
    `C:////Users////Lenovo////...`，`"%PY%"` 变成字面量字符串
- **为什么 `if not exist` 没兜住**：`if not exist "%%PY%%"` 里的变量名本身就错了，
  判断的是 `%PY%`（空），永远为真 → 直接 goto nopy 打印"找不到"。
- **★ 关键教训：只验证"纯 ASCII + CRLF"是不够的。**
  我当时的自检是
  ```python
  print('纯ASCII:', all(x<128 for x in b), ' CRLF:', b.count(b'\r\n'))
  ```
  两项都通过，文件仍然是坏的 —— **编码对 ≠ 内容对**。
- **正确自检**（三条都要）：
  ```python
  # ① 含变量名的行，除 for 语句外，单个 % 才是对的
  for ln in t.split("\n"):
      if ln.strip().lower().startswith("for "): continue   # for %%i 合法
      assert "%%" not in ln, "变量名双写了: " + ln
  # ② 盘符路径里不能有连续两个斜杠
  assert not re.search(r'[A-Za-z]:[\\/]{2,}', t)
  # ③ 真正跑一次
  subprocess.run(["cmd", "/c", bat], timeout=60, input="")
  ```
- **那次是怎么发现的**：用户双击后截图发我。**17 个 .bat 里 5 个是坏的**，
  而其中 3 个（run_ifft / run_ovl / run_win）因为 `C://` 被 Windows 规范化了、
  又走 `for /f where python` 兜底，**一直是能跑的** —— 所以坏了几周没人发现。
  真正坏的 4 个（run_demo_weak / run_scan_snr / annotate_photo / run_demo_sensor）
  是缺兜底路径的。
- **修法**：生成时用 `%` 单个、`\` 单个；或用 Write 工具直接写文件（不经 Python 字符串）。
- **顺带修的体验问题**：所有演示脚本原先硬编码 `COM5`，
  板子换口就报 `could not open port 'COM5'`，而这句报错
  **看不出是"端口名不对"还是"板子没插"**。抽了 `host/port_pick.py`：
  CH340/USB-Serial 优先、蓝牙虚拟口排最后，找不到时列出所有串口并标注哪个是蓝牙。
- **来源**：WaveCore 2026-10-25（用户点 annotate_photo.bat 报错）

## SK-084 · 校验和把帧头也算进去了 —— 一类帧全部被丢弃

- **现象**：上位机勾了"启用锁相"，读数一直停在"正在读取…"，永远不出来。

  ```verilog
  // 错的

  // 对的
  body[21] = body[2] + body[3] + ... + body[20];
  ```
- **为什么结果恒差 1**：`5A + A5 = 0xFF`，模 256 相当于 **−1**。

- **为什么一直没发现**：
  1. 上位机 `parse_lockin_frame` 校验失败 → 抛 `protocol_error` → **静默丢弃**，

- **★ 规则一：多帧类型共存时，校验和口径必须统一，且要有审计器守住。**

- **★ 规则二：解析器校验失败要吵闹，不能静默丢弃。**
  现在改成了把 `protocol_error` 事件也显示出来。
  否则"不显示"和"算错了"在用户眼里是同一件事。
- **修法（两步，都要）**：
  1. 改 RTL 与其他帧对齐（根治，但要重新综合才生效）
  2. 解析器**同时接受两种口径**（旧固件已烧进 Flash 的板子不用重烧就能用）
- **来源**：WaveCore 2026-10-25（用户问"为什么一直显示正在读取"）
