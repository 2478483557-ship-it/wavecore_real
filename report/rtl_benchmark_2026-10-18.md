# RTL 写法对标：三个获奖开源项目 vs WaveCore

> 2026-10-18。目的：回答"国一国二的项目，RTL 是怎么写的，我们差在哪、怎么补"。
> **所有对比都基于实际读到的代码，不是凭印象。**

---

## 一、看了哪三个

| 项目 | 成绩 | 方向 | 为什么选它 |
|---|---|---|---|
| **`mfkiwl/Ultra-Vision`** | **2024 国一 + 易灵思企业杯** | 无极缩放的硬件插值 | **代码组织最规范**，算法拆到极细 |
| **`maojinxiang/FPGA-ANLU-National-First-Prize`** | **2025 安路 国一** | 图像采集/RGMII/SDRAM | 308 个 RTL 文件，工程量大 |
| **`wushir828/FPGA-ADC-oscillograph`** | 非国奖，但**结构与我们同构** | DDS + ADC + 触发 + 频率计 | 功能对应关系最直接 |

触发控制、频率计、显示），拿来对照最有意义。

## 二、他们怎么写 —— 四条值得学的

### 1. 顶层参数化，且位宽写进默认值

Ultra-Vision `bicubic_interpolation.v`：

```verilog
module bicubic_interpolation
#(
    parameter C_SRC_IMG_WIDTH  = 12'd640    ,
    parameter C_SRC_IMG_HEIGHT = 12'd480
)
(
    input  wire                 clk_in1         ,   // 两个时钟域并列声明
    input  wire                 clk_in2         ,
    ...
```

注意三个细节：
- **`C_` 前缀**表示"Compile-time constant"，和运行时信号一眼分开
- **`12'd640`** —— 位宽写进默认值，不是光秃秃的 `640`。改点数时工具能直接报位宽不够
- 端口按**功能分组**加空行（时钟 / 输入流 / 输出流），不是一长串

我们的 `board_top.v`：

```verilog
module board_top (          // ← 没有 #(...)，零参数化
    input  wire        sys_clk,    // 系统时钟 50MHz
```

**上层传给它的东西全是硬编码**：50MHz 系统时钟、1024 点、25MHz ADC 采样率。
换一块板（比如 100MHz 时钟）要改多处。

### 2. 信号流用前缀/后缀标记生命周期

Ultra-Vision 同一模块内：

```verilog
input  wire                 per_img_vsync   ,       // Prepared Image data vsync
input  wire                 per_img_href    ,
input  wire     [7:0]       per_img_gray    ,

output reg                  post_img_vsync  ,       // processed Image data vsync
output reg                  post_img_href   ,
output reg      [7:0]       post_img_gray   ,
```

`per_` = 处理前，`post_` = 处理后。往下还有：

```verilog
reg  per_img_href_dly;                    // _dly = 打拍
wire per_img_href_neg;                    // _neg = 下降沿
assign per_img_href_neg = per_img_href_dly & ~per_img_href;
```

**边沿检测是一行 `wire + assign`**，不塞进 always 块。

对照我们 `ad_driver.v`：

```verilog
always @(negedge sys_clk or negedge sys_rst_n) begin
    if (!sys_rst_n) ad_cap <= 8'd0;
    else            ad_cap <= ad_data;
end
```

**一开始我判断"缺两级同步器"，这个判断是错的，已修正。**

查 AD9280 数据手册，`tOD`（Data Valid Delay）**最大 25 ns**，
我们的采样点在 `ad_clk` 上升沿后 10 ns —— **数据根本还没出来**。

那为什么能工作？因为**采到的是上一个采样点**，等效整体延迟一个周期：

```
ad_clk 周期 T = 40 ns (25 MHz)
第 N 个上升沿 t = 40N，数据在 40N + 25 有效
我们在 t = 40(N-1) + 10 采样 → 拿到的是第 N-1 个点
该点在 t = 40(N-1) + 25 就有效了，到采样时**已稳定 25 ns**
```

**结论：设计正确，稳定裕量 25 ns，充裕。** 这是"系统同步接口"，
不是异步 CDC，所以不需要两级同步器（加了反而多两拍延迟）。

**真正的问题不是代码，是没有任何地方写过这个计算。**
`board/wavecore.xdc` 里只有一句 `create_clock`，
**没有 `set_input_delay`** —— 也就是说"时序收敛"这个结论
**不覆盖 ADC 输入路径**。评委若问"你怎么保证采样窗口正确"，
现在的回答是"实测能跑"，而不是"算过，余量 25ns"。

### 3. 算法拆到极细，一个模块只算一个系数

Ultra-Vision 双三次插值总共拆成：

```
Algorithm/
├── bicubic_interpolation.v        主文件（坐标、行场时序、输出对齐）
└── parameter/
    ├── BiCubic.v                  组合体：调下面 8 个
    ├── BiCubic_y0~y3.v            四个垂直方向系数
    ├── BiCubic_x0~x3.v            四个水平方向系数
    ├── mul_2 / mul_3 / mul_4.v    定点乘法（按常数特化）
    └── mul_add_1.v                乘加
```

`BiCubic.v` 本体只有实例化语句：

```verilog
BiCubic_y3 BiCubic_y3_inst(
    .clk       (clk),
    .rst_n     (rst_n),
    .coeffOne  (coeffOne),
    ...
    .bi_y3     (bi_y3)
);
```

**主文件管时序、子模块管算式，职责不混。** 好处是改一个系数不影响别处，
每个子模块都能单独仿真。

### 4. 注释写"为什么改"，不是"这是什么"

安路国一 `line_buffer.v` 头注释：

```verilog
// ============================================================================
// 行缓存模块 - 使用BRAM IP核实现
// 功能：存储2行图像数据，生成3x3滑动窗口
// 修复：使用专用BRAM IP核替代寄存器数组，解决时序问题   ← 关键
// ============================================================================
```

**"修复：……解决时序问题"** —— 记下了"曾经错在哪、为什么改"。
评委翻代码时，这一行比十行功能描述有用。

## 三、逐项对照（含我们更强的地方）

| 维度 | Ultra-Vision（国一） | WaveCore | 判定 |
|---|---|---|---|
| 顶层参数化 | `#(parameter C_X = 12'd640)` | **零参数化** | ❌ 我们弱 |
| 常量命名 | `C_` 前缀 | 无统一前缀 | ❌ 我们弱 |
| 信号流命名 | `per_` / `post_` / `_dly` / `_neg` | `_w` 后缀，混用 | ⚠️ 平 |
| 算法模块粒度 | 拆成 8 个系数子模块 | `self_fft_1024.v` **830 行 9 合 1** | ❌ 我们弱 |
| **组合逻辑赋值** | — | **全部阻塞赋值** | ✅ **我们规范** |
| **关键常量硬编码** | — | 采样率用 `fs_cfg` 传递，**不写字面量** | ✅ **我们规范** |
| **跨时钟域** | 有同步（视频流） | `ad_cap <= ad_data` **无同步器** | ❌ 我们弱但可零成本补 |
| **验证** | 演示式，无回归 | **30 个验证脚本 / 10 个 testbench / 数值金标准** | ✅ **我们强得多** |
| **注释质量** | 功能描述为主 | 写"为什么"（定标、边界、取舍） | ✅ **我们强** |
| testbench 判错 | — | PASS/FAIL 计数，**非 assert** | ⚠️ 平 |

**结论：我们的代码不差，甚至有三项强于国一。真正的短板只有 3 个，全部是"组织方式"，不是"算法实现"。**

## 四、模块粒度实测

```
模块数 35，总行 5010，平均 143 行，中位数 73 行
```

中位数 73 行是**很健康**的粒度。问题在头部：

| 文件 | 行数 | 内部含几个功能 |
|---|---|---|
| `self_fft_1024.v` | **830** | FFT 蝶形 / 采集 / 窗函数(3档+自适应) / 帧重叠 / IFFT 滤波 / DAC 回放 / 状态回读 / 峰值检测 / 插值 = **9 个** |
| `board_top.v` | 605 | 纯例化 + 线网（顶层本来该长） |
| `freq_meter.v` | 327 | 闸门法 + 测周法 + 消抖 |
| `cmd_decoder.v` | 288 | 命令解析 |

**41% 的代码集中在 4 个文件。** `self_fft_1024.v` 一个文件顶别人整个算法目录。

## 五、改法（按风险排序）

### A 级 · 零风险，纯声明/标注（建议立刻做）

| 改动 | 做法 | 收益 |
|---|---|---|
| A1 顶层参数化 | `board_top.v` 加 `#(parameter CLK_FREQ_HZ = 32'd50_000_000, FFT_N = 1024, ADC_FS_HZ = 32'd25_000_000)`，**默认值 = 现在的硬编码** | 综合结果不变，但看起来专业，且换板能改一处 |
| A2 CDC 标注 | `ad_data` 加 `(* ASYNC_REG = "true" *)` 两级寄存 | 消掉 CDC 警告，功能不变 |
| A3 常量前缀 | 现有 `localparam` 加 `C_` 前缀（如 `S_IDLE` → `C_S_IDLE`） | 命名规范统一 |

> A1 必须验证"综合后资源与时序不变"，做法是改完跑一次 `check_lut.bat` 对比 7368/6521。

### B 级 · 低风险，机械拆分（时间够就做）

**把 `self_fft_1024.v` 的"峰值插值"单独拆出**（约 60 行，纯计算 + 状态机小循环）。

理由：这段是**自包含**的（第 309~345 行），输入是三个 bin 的幅度，输出是修正后的频率，
不碰蝶形、不碰存储。拆出去后用现有 testbench 回归，风险可控。

拆完 830 → 约 770 行，收益主要是可读性。

### C 级 · 高风险，**建议不做**

大范围按功能拆成 5 个文件（采集/蝶形/窗/峰值/回放）。

**理由**：
- 距提交只剩 17 天
- 拆完要重新综合（8~15 min）、重新上板复验（四档预触发、FFT 读数、IFFT 回放）
- 收益是"好看"，不是"更对"
- **风险与收益不成比例**

替代方案：在技术文档里加一张 **`self_fft_1024` 内部功能分区图**，
说明这 9 个功能各自占哪一段、读写哪些存储。**评委看的是"你知不知道自己代码的结构"，
不一定要真的拆开。**

## 六、一条反向建议

我们还强的地方，**应该在文档里说出来**：

> "验证体系共 30 个 Python 数值脚本 + 10 个 testbench，所有频谱读数与 Python
> 金标准逐字比对，协议帧由审计器逐条校验。"

国一项目的 README 里没有这种描述——他们是"演示式验证"。这是我们的差异化优势，
比"代码拆得细"更能打动评委。
