## ★ 前置补丁（2026-09-30 深夜，**已修，优先级高于本方案所有项**）

在写本方案时顺手复查了频率换算代码，**发现并修复了一个从未被测出来的静默错误**。

### 症状
`self_fft_1024.v` 与 `fft_demo.v` 的频率换算写成了 24 位乘法：

```verilog
// self_fft_1024.v（自研通路，N=1024）
res_freq <= (pk_bin*24'd50000)>>10;
// fft_demo.v（IP 通路，N=4096）
fft_hz   <= ((peak_bin * 16'd50000) + 12'd2048) >> 12;
```

按 Verilog LRM（IEEE 1364-2005 §5.4.1/§5.4.2）：乘法结果位宽 = `max(操作数位宽)`，
**但在赋值语句里右式会被提升到左值的位宽** —— 所以这两处实际都是按 **24 位**相乘。

| 通路 | 24 位上限 | 实际需要 | **溢出起点** |
|---|---|---|---|
| IP（N=4096, Δf=12.2Hz） | 16,777,215 | 4095×50000 = **204,750,000** | **bin ≥ 336 → 4102 Hz** |
| 自研（N=1024, Δf=48.8Hz） | 16,777,215 | 511×50000 = **25,550,000** | **bin ≥ 336 → 16406 Hz** |

### 为什么一直没被发现（这也是最该记住的一条）
1. **症状是"看起来正常的错数"**：截断丢掉的是 `2^24`，再 `>>10` 后**恰好偏 −16384 Hz**。
   不报错、不乱跳，就是一个"像个频率"的数字。
   ```
   bin 335 -> 16357 Hz  正确
   bin 336 ->    22 Hz  正确应为 16406   （偏 -16384）
   bin 511 ->  8567 Hz  正确应为 24951   （偏 -16384）
   ```
2. **之前所有上板测试都在低频**：1kHz（自研 bin20 / IP bin82）、方波 3 次谐波 3kHz（IP bin246）、
   扫频 800~1200Hz —— **全部低于 4102 Hz**，一个都没踩到。
3. 测频到 1MHz 用的是 `freq_meter`（纯边沿计数），**根本不经过这两条换算**。

★ **净影响：修复前，IP 通路（`S=`/`A=`，也就是主频谱读数）在 4.1kHz 以上全是错的；
自研通路（`SF=`）在 16.4kHz 以上是错的。** 只要演示时把信号调到 5kHz 就会暴露。

### 修复
乘数与加数整体加宽到 32 位；代价是乘法器由 10×24 / 14×24 变 10×32 / 14×32，**各占 1 个 DSP**（当前 28/90，余量充足）。

```verilog
res_freq <= (pk_bin*32'd50000)>>10;
fft_hz   <= ((peak_bin * 32'd50000) + 32'd2048) >> 12;
```

### 验证（不是"我觉得对"，是逐点算过）
- 数据模型与**板上实测逐字吻合**：IP 1kHz → 模型 1001 = 板上 `S=0001001`；自研 1kHz → 模型 976 = 板上 `SF=0000976`。
  （模型对了，才能用它判断其余 4095 个 bin 对不对）
- 全 bin 扫描：IP 通路 **3760/4095 个 bin 原来是错的 → 修复后 0 错**；
  自研通路 **176/511 个 bin 原来是错的 → 修复后 0 错**。
- 工具：`hw_analysis/check_self_fft_overflow.py`、`hw_analysis/verify_freq_conv_fix2.py`
- **新增回归场景 F**（`sin400.hex`，bin 400）：修复前会报 3147Hz，修复后报 19531Hz。
  原来 5 个场景全在 bin ≤ 100，**根本抓不到**（又一次 SK-034"测试覆盖不到就等于没测"）。
  `xvlog` + `xelab` 已过；执行待双击 `sim/fft_check/run_fft_check.bat` 看 **`PASS=6 FAIL=0`**。

### 因此，执行顺序要插一条
**第 0 步（最高优先）：重新综合 + 烧板，用 5kHz / 10kHz 信号复验频率读数正确。**
在这一条通过之前，**不要**开始做下面任何一项新功能 —— 否则拿一个"4kHz 以上读数错"的版本去叠加新功能，
一旦出问题会分不清是谁的锅。

复验判据（可直接粘贴，460800-8N1）：
```
设 10kHz : 5A A5 85 00 04 10 27 00 00 C0
正弦     : 5A A5 88 00 01 00 89
跑IP FFT : 5A A5 8A 00 01 01 00 8C      (0x8A 负载 0x01 = IP 通路)
跑自研FFT: 5A A5 8A 00 01 00 8B
```
- **修复前**：10kHz 正弦，`S=` 会报约 1806Hz（错得离谱）
- **修复后**：`S=` 应报 **9998Hz 左右**（10000/12.207 = bin 819 → 9998Hz），`SF=` 应报 **9960Hz 左右**（10000/48.828 = bin 204 → 9960）
- **顺带**：这时 `S=`（IP 4096 点，Δf=12.2Hz）会比 `SF=`（自研 1024 点，Δf=48.8Hz）更接近真值 10000 —— 这正是"点数多分辨率高"的直接证据，答辩可用。

> ⚠️ 上面帧里的 0x8A 负载字节请以 `board/uart_protocol.md` §6 为准复核一次

## 〇、先纠正一个直觉误区：**"分辨率不够"不等于"点数不够"**

这是本次评估最重要的一条，先说清楚，因为它决定了 4096 点该排第几。

**基本关系：**

```
Δf = fs / N        = 1 / T
T  = N / fs   （观察时间）
```

所以 **分辨率只由"观察时间 T"决定**，跟"点数 N"不是一对一关系。把 N 翻 4 倍，
如果同时把 fs 也降 4 倍，Δf 一样，但资源一点没多花。

| 方案 | N | fs | Δf | 观察时间 T | 资源增量 | 能看多宽 |
|---|---|---|---|---|---|---|
| **现状** | 1024 | 50 kHz | **48.8 Hz** | 20.5 ms | — | 0~25 kHz |
| **A. 只加点数** | 4096 | 50 kHz | **12.2 Hz** | 81.9 ms | **+5 块 BRAM** + IP 重定制 | 0~25 kHz |
| **B. 只降采样率** | 1024 | 12.5 kHz | **12.2 Hz** | 81.9 ms | **0** | 0~6.25 kHz |
| **C. 两者都做** | 4096 | 12.5 kHz | **3.05 Hz** | 327 ms | +5 块 BRAM | 0~6.25 kHz |

> **看出关键了吗**：A 和 B **分辨率、观察时间完全一样**，差别只有两点：
> ① A 要多花 5 块 BRAM 且必须重定制 Vivado IP；② **A 能同时在 0~25kHz 全带宽下保持细分辨率，B 只能看低频段。**
>
> 所以 **4096 点唯一的不可替代价值 = "宽带 + 细分辨"同时成立**。
> 而我们的演示信号（1kHz 正弦/方波，最高演示到 1MHz 方波）**根本不需要在全带宽下细分辨**——
> 想看 1kHz 附近的细节，把 fs 降到 6.25kHz 就够（Δf=6.1Hz，比 4096@50k 还细 2 倍，且零成本）。

**结论：把"降采样率"（= 时基档位，协议里 `0x8D` 已预留）先做了，4096 点的必要性就掉一大半。**
4096 不是错，是**性价比排在后面**。

## 二、逐项细化

### 2.1 🥇 `0x8E` 幅度谱帧 + 频谱图（**第一优先**）

**为什么排第一：**
- 外部评审原话就是"**频谱展示力度不足**"。现在 FPGA **只上报 3 个峰值数字**（`SF/S2/S3`），
  上位机**根本画不出频谱图**——这不是画图能力问题，是**数据源缺失**（`upgrade_v2_plan.md` §5.1 已定性）。
- 演示视频最需要的"王炸画面"：**频谱柱状图 + 瀑布图**（扫频时瀑布图上出现一条斜线）。
- 协议里 **`0x8E` 已经预留好**，不撞号。
- **纯增量**：新增一个状态机 + 一个小 RAM + 一个上行帧类型，**完全不碰**现有的测量/波形/FFT 通路 → 回归风险最低。

**设计（比 v2 计划更省、更清楚）：**

```
上行帧：5A A5 02 02 00 + 512 字节(幅度, 8bit 对数压缩) + SUM
                        └ LEN = 0x0200 = 512
帧长 = 2 + 3 + 512 + 1 = 518 字节 → 518 × 10 bit ÷ 460800 = 11.2 ms/帧
→ 理论 89 帧/s，实用 10~20 帧/s（链路占用 <25%）
```

**关键改进点（相对 v2 的 256 点方案）：**

| 项 | v2 计划 | **本方案** | 理由 |
|---|---|---|---|
| 点数 | 256（每 4 bin 取最大，有损） | **512（全分辨率）** | 实数输入的 FFT 输出**共轭对称**，`X[k]=conj(X[N-k])`，**只要发 k=0..511 就完整覆盖 0~fs/2**，不需要压缩 |
| 帧长 | 262 B | 518 B | 仍然只占链路的 25%，换回全分辨率 |
| 频率轴 | `f_k = k×(fs/256)` | `f_k = k×(fs/1024)` | 与 FFT 原生 bin 一一对应，答辩好解释 |

**8bit 对数压缩（几乎不花资源，关键技巧）：**

不查表、不做除法，用**"前导零 + 桶形移位"**实现分段对数：

```
mag = |re| + |im|            // L1 模，与现有找峰判据同一口径，不新增运算
b   = mag 的最高有效位位置    // 优先编码器（约 20 LUT）
m4  = (mag << (15-b)) >> 12  // 把 msb 对齐到 bit15，取接下来 4 位
y   = b*16 + m4              // b∈[0,15] → y∈[0,255]，完美填满 8 位
```

- 每倍频程 16 级 → 步进 **0.38 dB**，动态范围 **96 dB**，够画任何谱
- 成本 ≈ **60~80 LUT + 1 个桶形移位器**，不用 DSP、不用 BRAM 查表
- 顺序扫描时顺手写进一个 **512×8 的双口 RAM**（用 LUTRAM 或半个 BRAM 即可）

**改动清单：**

| 文件 | 改动 | 规模 |
|---|---|---|
| `src/self_fft_1024.v` | 扫描状态机里顺手输出压缩幅度 + 写指针；新增 `spec_we/spec_addr/spec_data` 端口 | ~40 行 |
| **新增 `src/spec_compress.v`** | 前导零 + 移位 + 拼接 | ~40 行 |
| **新增 `src/spec_buf.v`** | 512×8 双口 RAM（或用 `ram_style` 推断） | ~25 行 |
| `src/cmd_decoder.v` | 新增 `0x8E` 解析 → `spec_req` 脉冲 | ~10 行 |
| `src/board_top.v` | 连线 + 触发"发送 512 字节谱帧"状态机 | ~50 行 |
| `src/uart_tx.v`（或现有上报模块） | 复用现有 1024 字节波形帧的发送机制，改成 512 字节 | ~20 行 |
| `host/wavecore_gui.py` | 频谱柱状图 + 瀑布图（队友1） | — |
| `board/uart_protocol.md` | 升 **v1.18**，补上行帧 3 与 §4.1 | — |

**验收标准：**
1. 发 `0x8E` → 收到 **518 字节**、`SUM` 正确的谱帧（帧头 `5A A5 02 02 00`）
2. 1kHz 正弦 → 图上**只有一根竖线**在 1kHz 位置，其余是噪声底
3. 1kHz 方波 → **三根竖线**在 1k / 3k / 5k，且 3k 比 1k 低约 9.5dB、5k 再低约 4.5dB（方波理论值 1/n）
4. 扫频（`0x8B`）时瀑布图出现**一条斜线** ← 这就是演示视频的"王炸画面"

### 2.2 🥈 `0x8D` 时基档位（fs 可调）

**为什么排第二：** 这是**示波器的标配能力**，也是外部评审点名的第一项。而且它**顺带解决"分辨率"问题**（见 §〇）。

**档位表（建议，先用保守的 5 档）：**

| 档 | DECIM | fs | 1024 点 Δf | 观察窗 T | 覆盖 |
|---|---|---|---|---|---|
| **T1** | 1000 | 50 kHz | 48.8 Hz | 20.5 ms | 0~25 kHz（**现状，上电默认**） |
| T2 | 4000 | 12.5 kHz | 12.2 Hz | 81.9 ms | 0~6.25 kHz |
| T3 | 500 | 100 kHz | 97.7 Hz | 10.2 ms | 0~50 kHz |
| T4 | 50 | 1 MHz | 977 Hz | 1.02 ms | 0~500 kHz |
| T5 | 2 | 25 MHz | 24.4 kHz | 41 µs | 0~12.5 MHz（硬件极限） |

> T2 是"细分辨率"档，等价于 4096@50kHz 的效果，**零资源成本**。
> DECIM 最小取 2（`ad_cap` 每 2 个 sys_clk 更新一次，题面见 `src/ad_driver.v`）。

**⚠️ 这是本次唯一有"静默错误"风险的改动：**

```verilog
// 现在（self_fft_1024.v:346）—— fs 写死 50000
res_freq <= (pk_bin * 24'd50000) >> 10;
                       ^^^^^ 改了 fs 但不改这里 = 读数全错，而且看起来"很正常"
```

**对策（必须做）：**
1. 把 fs 做成 `timebase.v` 的一个输出常量 `FS_HZ`，所有换算**只引用它**，不许再出现字面量 50000；
2. 加**断言/自检**：上电后默认 T1，`FS_HZ = 50000`，行为与现在**逐位相同**；
3. 换算用 40 位中间量（`pk_bin` 最大 4095、`FS_HZ` 最大 25e6 → 4095×25e6 = 1.02e11 > 2^36，需要 37 位），
   **别用 24 位**，否则高位截断 —— 这是第二个静默错误点；
4. 全库搜 `50000` / `48.8` / `48.83` / `976` 等派生数字，一并处理（SK-033）。

**前置实验（必做，零风险）：** `python host/link_response_scan.py` —— 测模拟链路（DDS→AD9708→滤波/运放→AD9280）的真实频响，**用曲线决定各档能不能用**，而不是假设。
（DAC 端 50MSPS 阶梯输出，模拟链路可能只有几十~几百 kHz 带宽；没有抗混叠滤波，**低 fs 档要标注"可能混叠"**。）

**改动清单：** 新增 `src/timebase.v`；改 `wave_frame.v`（`dcnt==999` → `decim-1`）、`fft_demo.v`（`DECIM` 常参→寄存器 + 换算）、`self_fft_1024.v`（同上）、`cmd_decoder.v`（`0x8D`）、`board_top.v`。约 **150 行**。

**验收：** 各档设 1kHz 方波，波形图上周期数 = `fs × 20.48ms / 1000`（T1 看到 20 个周期，T5 看到 1 个）；**不改档时与 v1.17 逐位一致**。

### 2.3 🥉 频谱插值（把 `976` 修正到 `1000`）—— **最便宜的高分项**

**问题**：现在 1kHz 正弦报 `SF=0000976Hz`，而真值是 1000Hz —— **误差 2.4%**。
评委一眼就能看出来"你这频率测得不准"。虽然旁边 `F=0001000Hz`（`freq_meter` 计数法）是准的，
但**频谱读数偏 2.4% 这件事本身就是可被质疑的点**。

**原理**：谱峰不是尖的，是主瓣。用峰值左右各 1 个 bin 的幅度做**抛物线插值**，
可以把频率估计精度从"±0.5 bin"提到"±0.02 bin"量级：

```
δ = 0.5 × (|X[k-1]| − |X[k+1]|) / (|X[k-1]| − 2|X[k]| + |X[k+1]|)
f = (k + δ) × Δf
```

- 期望效果：`SF` 由 `976` → **≈ 998~1000**（误差 2.4% → 0.2% 以内）
- 成本：**4 个减法 + 1 个除法 + 1 个加法**。除法用**倒数查表**（或直接 `÷`，Vivado 会用 DSP 搭）——
  现成 8 位精度足够，约 **2 个 DSP + 80 LUT**
- 这个改动**小而漂亮**，答辩时是"我懂频谱估计"的直接证据
- 注意：**只改自研通路**（IP 通路的 `S=` 由 IP 核自己报，不动），改完要重算 `sim/fft_check` 期望值（SK-037）

### 2.4 THD 总谐波失真

**问题**：一个"信号测量系统"没有 THD，功能上缺一块。而**数据已经在手上了**（`SF/S2/S3` 三峰）。

```
THD = sqrt(V2² + V3² + ...) / V1      （只算到 3~5 次谐波时标注 "THD(至5次)"）
```

- 需要同时上报**峰值幅度**（现在只报频率，`pk_best/m2/m3` 已经在寄存器里，加一行 `H=` 报出去）
- 成本：**很低**（3 个乘法 + 开方，开方可用 CORDIC 或查表；或直接报 `THD%` 用现成 DSP）
- 价值：**方波测 THD 应该 ≈ 42%**（理论上 sqrt(1/9+1/25+1/49) ≈ 0.42），
  这既是一个功能，**又是一个自检**（如果算出来不是 42%，说明通路有问题）
- 演示亮点：**用 THD 反证"我们的频谱是真的准"**

### 2.5 `0x8F` 预触发

- 现状：触发后写指针归零，帧首 = 触发点（**看不到触发前发生了什么**）
- 改法：1024 深**环形缓冲**常写，触发时记下地址，再写 N 点后停 → 从 `触发地址 − 预触发点数` 起读出
- 比例：0% / 25% / 50% / 75%
- 成本：`wave_frame.v` 约 **40~60 行**，**零 BRAM 增量**
- 价值：**"能看到触发前发生了什么"是示波器的标志性能力**，演示观感提升明显
- 风险：中（动了已经上板验证过的触发通路）→ 建议在 #1 #2 之后做

---

### 2.6 ⏸ 4096 点自研 FFT —— **诚实结论：排在最后，且"不做也行"**

**说清楚它到底要花什么：**

| 项 | 具体 |
|---|---|
| ① 存储 IP 重定制 | `blk_mem_gen_1` 是 **Vivado IP**（1024×32 → 需要 4096×32）。**必须在 GUI 里重新定制**，命令行环境的脚本做不了 |
| ② 旋转因子表 | 1024 → **2048 项**（4096 点 radix-2 DIF 第一级需要 2048 个），重新生成 + 数值验证 |
| ③ 窗表 | 需要 **4096 点 Hann**；而现有 `hann_1024.hex` 是**和 IP 通路共用的**（`fft_demo.v:93` 也在读它）→ 不能改，必须**新增**一份表和 ROM 文件 |
| ④ 地址/级数 | 10 位 → 12 位、`rev10()` → `rev12()`、**10 级 → 12 级蝶形**、所有计数器位宽 |
| ⑤ 频率换算 | `>>10` → `>>12`，且要和 #2 的变 fs 一起处理（40 位中间量） |
| ⑥ 资源 | 存储 4 块 RAMB36 + 旋转因子 2 块 + 窗 2 块 = **+5~6 块 BRAM**（11 → 16~17 / 50） |
| ⑦ **回归重做** | `sim/fft_check` **5 个场景全部重做**：激励表、期望值、判据；`hw_analysis/verify_hann_window.py` 数值模型也要改 → **正是 SK-037 那个坑的放大版** |
| ⑧ **互证链断掉** | 自研 4096 点 vs IP 1024 点，**两条通路不再能逐字互证**——而"双通路互证"是本项目最强的证据之一 |
| ⑨ 资源分反噬 | 资源占 **20 分**。任何"纯堆资源"的改动都会**主动降低资源分**，而收益（全带宽下的细分辨率）评审未必给分 |

**为什么"不做也行"：**
- 演示信号（1kHz 正弦/方波、扫频）在 T2 档（fs=12.5kHz）下 Δf=12.2Hz，**已经是 4096@50kHz 的效果**；
- 想在宽带上细分辨的场景（比如"10kHz 附近两个相隔 20Hz 的分量"）**我们的信号源做不出来也不需要**；
- 而**投入的时间**（IP 重定制 + 全套回归）**可以用来做 #1~#5 五项**。

**所以建议：把 4096 放进"如果 #1~#5 都做完了、且离提交还有一周以上"的候补区。**
如果最后还是想做，**做成"1024/2048/4096 可选"**比"直接改成 4096"好得多（多一个档位 = 多一个功能），
但成本也翻倍。

## 四、给报告/答辩准备的三句话（本方案落地后可直接用）

1. **"分辨率与带宽是一对矛盾，我们的做法是给用户一个时基档位（`0x8D`），
   让他在'看得宽'和'看得细'之间自己选，而不是把点数堆上去。"**
   （`Δf = 1/T` 的物理本质讲清楚，比"我做了 4096 点"有说服力得多）
2. **"频谱不再只是三个数字，而是一条完整曲线（512 点谱帧，11 ms/帧），
   扫频时瀑布图上能看到一条斜线。"**
3. **"频率读数用抛物线插值从 ±0.5 bin 修正到 ±0.02 bin，1kHz 从报 976Hz 变成报 999Hz；
   方波 THD 实测 ≈42%，与理论值 sqrt(1/9+1/25+1/49)=42.1% 吻合——这是对我们整条信号链的自检。"**
