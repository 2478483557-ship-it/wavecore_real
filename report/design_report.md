## 1. 选题背景与创新点

### 1.1 背景与问题
"口袋仪器"（信号源+测量+频谱一体）在实验教学、嵌入式调试与现场检测中有明确需求：传统方案要么靠昂贵台式仪器，要么用 MCU 方案牺牲实时性与精度。FPGA 的并行性、确定性时延与可重构能力，恰好匹配"多参数并行测量 + 频谱分析 + 实时触发"的任务形态。

我们对同类公开作品做了对标（`report/benchmark.md`）：官方命题类赛题竞争集中；而"完整测量链路 + 频谱"方向公开作品较少，**多为一机单功能**（或仅有频谱、或仅有信号源）。本项目选择"一机集成"路线，并在工程完备度上做深。

### 1.2 主要创新点
1. **一机集成"四台仪器"**：信号源、全参数测量、频谱分析、波形采集与触发，在同一颗 35T 上并行共跑；
2. **"同板双 FFT"对比**：厂商 4096 点 IP 与手写 1024 点 Radix-2 DIF FFT 同板并存，资源与精度同口径对比（自研核 502 LUT / 7 DSP，约为 IP 裸核的 1/3 资源；读数与 Python 金标准逐字一致）。自研核另做两件 IP 通路没有的事：**Hann 窗**把矩形窗 14.7% 的频谱泄漏压到 **0.9%**（根除非整数 bin 处的"假峰"），**抛物线插值**把频率读数从 976Hz 修到 **999Hz**（误差 2.4% → **0.1%**）；
3. **测量鲁棒性设计**：四层数字抗噪（2 拍确认 / 施密特迟滞 / 5 点中值 / 3 窗中值）+ **可信闸门**（测不准时输出"其他"而非错误结论）；
4. **工程方法论沉淀**：以"数据 → 假设 → 错误变体仿真 → 上板复现"的闭环定位根因，全过程沉淀 **38 条可复用技能包**。

### 2.3 关键原理（摘要）
- **DDS**：`f_out = fcw × 50MHz / 2^32`；查表取相位高 8 位（相位截断）。
- **测频**：高频用 10ms 闸门数周期（`f=N×100`）；低频切换测周法（数 32 个周期的时钟拍，`f=32×50MHz/N`），误差互补。
- **频谱**：帧截断加 **Hann 窗**抑制泄漏；FFT 蝶形 `O1=A+B, O2=(A−B)×W`，1024 点 = 10 级 × 512 只 = 5120 只蝴蝶（较朴素 DFT 快约 205 倍）。
- **触发**：检测边沿（对比上一拍电平）→ 指针归零 → 写满 1024 点，保证"帧首点=触发点"。
- **识别**：统计"近极端（>0.75 幅度）时间占比"：方波≈100% / 正弦≈46% / 三角=25%（比较器+计数器实现，零乘法）。

## 3. 软硬件划分依据与接口设计

### 3.1 划分依据
- **PL（FPGA）承担实时链路**：采样、测量、FFT、触发、识别、协议——任务并行且对时延确定性敏感（20ns 时间刻度）；
- **PC 上位机承担可视化**：波形显示、仪表板、频谱瀑布图（Spectrogram）——数据经 460800 串口直连；
- **预留 F1 转发口**：供 STM32 等外设镜像串口流（本阶段不启用）。
- 说明：本项目**不使用 PS/软核**，全部功能由 PL 逻辑实现——这是初级组"考察基本 FPGA 设计能力"定位下的主动选择。

### 3.2 接口设计（自定义帧协议 v1.21，全文见 `board/uart_protocol.md`）
- 帧格式：`5A A5 | TYPE | LEN_H LEN_L | PAYLOAD | SUM`（SUM=除帧头外全部字节求和取低 8 位）
- 下行命令（**25 条**）：0x81 档位 / 0x85 任意频率 / 0x87 双音 / 0x88 波形 / 0x89 触发 / 0x83 抓波 / 0x8A 自研FFT / 0x8B 扫频 / 0x8C 电压标定 / **0x8D 时基（固件四档）** / **0x8E 幅度谱帧请求** / **0x8F 预触发四档**……
- 上行行：`F=`／`D=W=`／`TY=`／`S=A=`／`SF=S2=S3=`／波形帧（1030B，≈22ms）／**幅度谱帧（518B 二进制，≈11.2ms）**
- 物理层：AD/DA 模块（AD9280/AD9708）并口；IO 电平按 Bank 约束（见 `src/wavecore.xdc` 与 `board/pin_map.md`）

### 4.1 资源优化（关键四轮）
| 阶段 | 问题 | 措施 | 结果 |

### 4.5 电压测量准确度的外部验证（2026-10-07）

以**信号发生器设定值为基准**（输出直接接 AD 模块输入端，摘除板内回环），在 1~4Vpp 四个幅度点上比较：

| 发生器设定 | 本机测量值 | 相对偏差 |
|---|---|---|
| 1.0 V | 1017 mV | +1.7% |
| 2.0 V | 1998 mV | −0.1% |
| 3.0 V | 2979 / 2942 mV | −0.7% / −1.9% |
| 4.0 V | 3887 mV | −2.8% |

- **最大偏差 2.8%，平均偏差 0.8%**
- 最小二乘拟合：`测量值 = 0.957 × 真值 + 72.5 mV`，**残差 ±16mV（±0.5%）** → **线性度优秀**
- 读数波动：3V 点两次读数差 1.2%，与"3 窗中值"平滑的滞后特性一致
- ★ **不确定度说明**：示波器（典型 ±3%）与万用表（交流档读数异常）**均不作为基准**；
  以发生器设定值（厂家标称 ±1%）为参考，**测量链路增益误差 < 3%**

### 4.6 触发判据修复与频率/占空比准确度（2026-10-07）

**（1）发现的问题**：原触发实现要求"相邻两拍"完成跨阈（≤120 → ≥136），
平缓边沿无法满足 —— 1kHz 正弦在 fs=50kHz 下**每拍仅变化约 3.5 个码**（需 16 个），
实测表现为"**方波能触发、正弦完全收不到波形**"。

**修复**：改用**状态位"蓄势"机制**——信号曾回到低电位即置位 `armed_lo`，
此后跨过高阈值即触发，触发后自动解除；下降沿对称处理。
**陡边沿下与原实现行为等价**（仍是单拍脉冲），故对方波无回归风险。

**验证结果**：

| 输入 | 触发 | 说明 |
|---|---|---|
| 方波 1 kHz | ✅ 正常 | 修复前后一致（无回归）|
| **正弦 1 kHz** | ✅ **正常** | **修复前完全收不到** |
| **正弦 100 Hz** | ✅ **正常** | 边沿更慢，修复效果更明显 |

**（2）频率与占空比准确度**（以信号发生器方波为基准，全量程测点）：

| 项目 | 结果 |
|---|---|
| **频率**（100Hz / 1k / 10k / 100k / 500k / 1MHz）| **全部命中，未观察到偏差** |
| **占空比**（20% / 50% / 80%）| **全部正确** |

> 说明：以上为 2026-10-07 外部基准测试结论；此前板内自测亦记录 1k→999、10k→9998、
> 20k→19995 Hz（相对误差 <0.1%）。

### 4.7 波形刷新率与采集死区量化（2026-10-07）

**背景**：波形缓存采用**单口 RAM**，发送期间采集暂停 —— 这是本设计的已知取舍。
若不量化，"连续采集"就只是一句宣传；量化之后它才是一个**可验证的指标**。

**方法**：连续发送 `0x83` 请求波形（**收到一帧立刻再要下一帧**，上位机不限速），
统计实际帧率。工具：`host/check_framerate.py`（一键 `run_check_framerate.bat`）。

| 项目 | 数值 |
|---|---|
| **实测** | 9.2 s 收到 **195 帧** → **21.2 帧/s**（**47.2 ms/帧**）|
| **理论下限** | 传输 1030B@460800 = 22.4 ms ＋ 采集 1024 点@50kHz = 20.5 ms → **约 43 ms/帧**（23.3 帧/s）|
| **实测效率** | **91%** ✓ |

**结论**：单口 RAM 方案下"采集与发送串行"带来的死区**很小**，
实测帧率达到理论值的 **91%**，在工程上可视为**准连续采集**。

**说明**：若后续改用**乒乓双缓冲**（两块 RAM 交替采集/发送），
理论上可让采集与发送并行，帧率上限可再提升约一倍 —— 已列入 §4 的可扩展方向。

### 5.1 工作流
现象/需求 → 与模型协作产出方案或代码 → **人上板实测** → 数据对照 → 若不符，进入"错误变体"复现式定位 → 修复 → 回写技能包。

### 5.2 三类典型协作（含自我纠错轨迹）
1. **"复现硬件式排障"（SK-025）**
   - 现象：自研 FFT 读数稳定但错误（1kHz → 1367Hz）
   - 轨迹：模型提出"读地址晚一拍/晚两拍"两种错误变体并仿真 → 变体恰在两组频率上逐字复现硬件输出（[1367,1318,1709]/[2686,3369,8740]）→ 锁定 BRAM 2 拍读延迟 → 修复找峰等待逻辑
2. **"工程语义陷阱"（SK-023）**
   - 现象：状态机"从未前进"（采集正常）
   - 轨迹：人工直觉怀疑"卡死"，模型按 Verilog 语义构建"default 覆盖赋值"变体 → 复现 → 修复（补空 case）
3. **"设计文档与代码一致性审查"（多次）**
   - 轨迹：模型全库审计发现"技能包清单缺失后 12 条""重复条目""陈旧状态未更新"等 → 当场修复

## 7. 复现说明

### 7.1 硬件清单
- 正点原子达芬奇Pro（XC7A35T-2FGG484）x1；高速 AD/DA 模块（AD9280 + AD9708）x1；USB 线；回环线（DA→AD）
- 可选：USB 转串口（板载 CH340 即可）；无需示波器亦可完成全部自测（回环+PC 交叉验证）

### 7.2 从零复现步骤（约 20 分钟）
```
1) git clone <repo>            # 纯英文目录结构
2) Vivado 2020.2 打开 → Tcl Console:
   source build/create_project.tcl     # 自动建工程+重建IP+重写hex路径
3) Run Synthesis → Implementation → Generate Bitstream
   预期资源（实现后）：LUT≈24.6%、FF≈11.6%、DSP=27、BRAM Tile=10；WNS>0
4) Program Device（或按 board/flash_guide.md 固化到 Flash）
5) 打开任意串口工具（460800-8N1）→ 观察 F=/D=W=/TY= 数据流
6) 按 board/uart_protocol.md §6 帧速查表发送命令（波形/频率/抓波/自研FFT/扫频）
7) 可选：运行 host/ 上位机脚本查看波形与测量
```
### 7.3 预期结果对照（与本文档数字一致）
- 1kHz 方波：`F=0001000Hz D=049.9~050.4% W=00005xx us TY=0`
- 1kHz 方波 + 0x8A：`SF=0000976 / S2=0002978 / S3=0004980`（bin20/61/102，±1 bin）
- 1kHz 正弦 + 0x8A：`SF=0000976 / S2=0000000 / S3=0000000`
  （正弦的 S2/S3 必须为 0；**非 0 说明板子上跑的还是修复前的旧固件**）
- 温度提示：正弦绝对占空比受模拟链路温漂影响（冷机≈50% → 热机≈46.8%），**测量基准请用方波**；详见 8.1

### 7.4 工具版本说明（官方要求非推荐版本的解释）
本工程使用 **Vivado 2020.2**（官方推荐 2026.1/2025.2）：
1. 达芬奇Pro 官方资料与例程基于 2020 系列，新手学习成本最低；
2. Artix-7 在 2020.2 支持完备，功能实现无差异；
3. **提供 `build/create_project.tcl` 保证脚本级可复现**，版本不影响他人复现核心流程；
4. 后期将评估新版兼容性并补充对比说明（如兼容则升级）。

## 8. 失败分析（诚实边界）

### 8.1 已知边界与解释
| 现象 | 原因 | 处理 |
|---|---|---|
| 正弦占空比 46.8~49.6%（随温度）| 模拟链路热平衡温漂（案例见 `report/engineering_challenges.md` 7.5）| 预热 3 分钟；方波为计量基准；终验用外部信号源 |
| >25kHz 频谱混叠 | 采样率 50kHz 设计使然 | TY 闸门报"其他"；多档 fs 列为可选扩展 |
| 自研 FFT 为迭代式（0.92ms/帧）| 面积换速度的主动取舍 | 采集窗 20.5ms 主导，按需运行足够 |

### 8.2 未完成/未实施（及原因）
- 音乐彩蛋（麦克风链路）：需额外硬件与资源（**资源攻坚前**主设计 LUT 占用 95.5%，
  现已降至 24.6%，资源不再是阻碍，但需额外麦克风硬件），列为可选；
- 高频段多档采样率、CRC 校验、自动重传：均已评估，属"排期未做"而非"未知"。

### 8.3 若重做一遍会改进什么
1. **更早核对"改的那一个东西"是否真的变了**——资源优化的第 4 轮（`f_ram` 未进 BRAM）
   本应在第 2 轮就被发现，却因只看总数被掩盖 25 天（详见 `report/lut_slim_report.md` §4.3.3）；
2. 更早引入统一仿真回归（当前依赖上板+PC 交叉验证为主）；
3. 报告与文档从第一天即按"官方目录规范"组织（本次后期已对齐）。

## 9. 后续可扩展方向

本设计的瓶颈已被**明确定位并量化**：波形缓存采用单口 RAM，**采集与发送串行**
（实测 47.2 ms/帧，效率 91%，详见 §4.7）。在现有硬件（Artix-7 纯 PL）条件下这一取舍合理，
但它同时指出了清晰的演进路径。

### 9.1 乒乓双缓冲（小改，收益直接）

用两块 BRAM 分别承担「采集」与「发送」，使两者并行：

| | 现状 | 乒乓后 |
|---|---|---|
| 每帧耗时 | 22.4 ms 传输 ＋ 20.5 ms 采集 = **47.2 ms** | ≈ **22.4 ms**（取较大者）|
| 帧率 | 21.2 帧/s | **≈ 45 帧/s** |

代价：一块额外 BRAM（当前仅用 11 块，余量充足）＋ 采集控制逻辑改动。

### 9.2 迁移 Zynq-7000 ＋ DDR ＋ 以太网（换平台，彻底解耦）

| 组件 | 解决的问题 |
|---|---|
| **PS 侧 DDR 缓冲** | 容量由 KB 级升至 MB 级，可做大深度乒乓，**彻底消除采集死区** |
| **以太网（100 Mbps）** | 相比 UART 460.8 kbps，带宽提升**约 200 倍** |
| 外置高速 ADC | 突破 25 MSPS，扩展可观察带宽 |

系统定位随之从「**便携测量仪**」升级为「**连续流式采集分析节点**」。

### 9.3 本设计已为该演进预留的条件（关键）

> **协议帧格式与上位机解析逻辑，与传输介质无关。**

- `board/uart_protocol.md` 定义的是**应用层帧结构**（帧头 ＋ 类型 ＋ 长度 ＋ 负载 ＋ 校验），
  可原样承载于以太网 / USB / SD 之上；
- 上位机 `host/protocol.py` 只依赖**字节流接口**，替换物理层无需改动解析与绘图逻辑；
- 采集通路的 `decim_cfg` / `fs_cfg` 参数化设计（§4.3）同样与传输方式无关。

因此本次沉淀的软件栈（**协议 / 上位机 / 验证脚本 / 技能包**）在平台升级后**可完整复用**。

### 9.4 为什么不在本次实现

**时间与风险**：离提交仅约 4 周，换平台意味着**重做全部已验证内容**（四档时基、预触发、
抛物线插值、电压标定、四层抗噪）；且 Zynq PS 侧开发（AXI 总线 / DDR 控制器 / lwIP 协议栈）
对新手存在较高学习成本。

> **在「稳定的完整」与「激进的重构」之间，本设计选择前者，并把路径记录清楚。**
> 这既是工程判断，也是对自己边界的诚实认知。
