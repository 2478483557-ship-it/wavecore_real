# T3/T4 时基上位机屏蔽 · 变更记录（2026-10-14）

> **一句话**：把 **T3(100kHz) / T4(200kHz)** 两档时基从**上位机**撤掉，
> 演示只保留 **T1(50kHz) + T2(12.5kHz)**。**FPGA 侧四档完全没动。**

---

## 一、为什么

用户实测：**切到 T3/T4 后，连 1kHz 信号都没反应**（T1/T2 正常）。
（此前 2026-10-11 也报过 "T2 运行不起"，后经电压/接线排查，T2 实际可用。）

> ⚠️ 注意与另一种现象区分：**"信号设成 100k/200kHz 时看不到谱线"** 是
> **采样定理的硬限制**（fs/2 = 100kHz，100kHz 正好落在奈奎斯特边界），**不是 bug**。
> 本次屏蔽针对的是**另一个现象**：切档后连低频信号也不响应。

## 二、代码排查结论（**没找到 bug**）

| 检查项 | 结果 |
|---|---|
| `src/timebase.v` 四档映射 | ✅ 正确（decim 1000/4000/500/250，fs 50k/12.5k/100k/200k） |
| `wave_frame.v` 抽取计数 | ✅ `reg [31:0] dcnt` 比较 `decim_use-1`，250/500 不溢出 |
| `self_fft_1024.v` 抽取 + 频率换算 | ✅ 32 位 `fs_use`，511×200000 = 1.02e8 不溢出 |
| `fft_demo.v`（IP FFT） | ✅ 同上 |
| 协议层 `TIMEBASE_SAMPLE_RATES` | ✅ 映射正确 |
| GUI `TIMEBASE_CHOICES` | ✅ 映射正确 |
| 工具 `TB_FS` | ✅ 映射正确 |
| **残留写死的 50000** | ✅ 无（SK-033/SK-038 的坑已清干净） |
| `spec_frame.v` 看门狗 | ✅ 25 位 / 335ms，对 T4 的 5.1ms 余量充足 |
| 磁盘 bitstream | ✅ `board_top.bit`（10-07 14:07）比所有 src 新，内容正确 |

**唯一可疑点**：`fft_report.v` 的固定窗口 `idle_cnt ∈ [3000, 350000]`
（`window_ok = !meas_busy && idle_cnt>=3000 && idle_cnt<=350000`）。
但它只管 **IP FFT 的 S/A 两行**上报时机，**不影响** 1kHz 的波形帧和 0x8E 频谱。

**最可能的解释（未证实）**：GUI 在切档后会**主动清空波形**并提示
"已切换T3，请重新请求1024点波形"。若切完没有重新点「请求1024点波形」，
画面就是空的 —— 视觉上等于"没反应"。

## 三、改了什么（**只动上位机**）

| 文件 | 改动 |
|---|---|
| `host/protocol.py` | `TIMEBASE_SAMPLE_RATES` 只留 0/1（2、3 注释掉）；`command_set_timebase` 对屏蔽档**抛 ValueError**；自检用例改为"验证 T3/T4 被拒绝" |
| `host/wavecore_gui.py` | `TIMEBASE_CHOICES` 只留 T1/T2；`_selected_timebase_index` 的错误提示改为**动态列出**当前选项 |
| `host/spectrum_waterfall.py` | `TB_FS` 只留 0/1；`--timebase` 的 `choices=sorted(TB_FS)` |
| `host/check_interp.py` | `--timebase` choices 改为 `[0, 1]` |
| `host/run_waterfall_T3.bat` | **删除**（git 可恢复） |
| `host/run_waterfall_T4.bat` | **删除**（git 可恢复） |
| `host/README.md` | §7 改"时基两档"；自检说明、bat 清单、断线重连用例同步 |

**刻意设计**：屏蔽档位**直接抛异常**而不是静默忽略。
理由：`0x8D` 是**静默命令（无 ACK）**，"发得出去但不生效"比"当场报错"难排查得多。

## 四、没改什么

- **FPGA 侧一行没动**：`timebase.v` 四档仍在，固件仍支持 T3/T4
- 因此 `design_report.md` / `feature_inventory.md` 等文档里"四档时基"的**描述依然成立**
  （那是**固件能力**，不是**上位机入口**）
- `host/link_response_scan.py` 里关于 T4 的注释保留（那是模拟链路频响实验的设计说明）

## 五、怎么恢复

1. `host/protocol.py`：把 `2: 100_000,` 和 `3: 200_000,` 两行**取消注释**
2. `host/wavecore_gui.py`：`TIMEBASE_CHOICES` 加回 `("T3  100 kHz", 2)` / `("T4  200 kHz", 3)`
3. `host/spectrum_waterfall.py`：`TB_FS` 加回 `2: 100000.0, 3: 200000.0`
4. `host/check_interp.py`：`choices` 改回 `[0, 1, 2, 3]`
5. `git checkout -- host/run_waterfall_T3.bat host/run_waterfall_T4.bat`
6. 跑 `python protocol.py` 确认自检通过

## 七、遗留问题（待查）

**切 T3/T4 后无响应的根因仍未定位。** 若后续要恢复这两档，建议按此顺序查：

1. 上电接回环飞线，切到 T3/T4，看**波形帧**是否有 1024 点回来（先排除 GUI 清空显示）
2. 看 `F=` 测量行是否仍在更新（`freq_meter` 不接时基，理论上必须正常）
3. 若波形帧正常但 0x8E 谱帧空白 → 查 `spec_frame.v` 看门狗与 `idle_cnt` 窗口
4. 用 ILA 抓 `tb_decim_w` / `tb_fs_w`，确认 0x8D 确实写进去了
