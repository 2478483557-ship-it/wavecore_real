# 串口"断电重连后打不开"的根因与解决办法（2026-10-21）

> **一句话**：不是串口被占用，是 **CH340 没有跟着板子一起断电**，
> 所以 USB 从未重新枚举，芯片卡在上一次上电冲击造成的不良状态里。
> **拔插 USB 线即可恢复，不用重启电脑。**

---

## 一、现象

```
板子插上 → 开电 → 串口正常
关电 → 再开电 → 串口打不开
只有重启电脑才能恢复
换队友的电脑不出问题
```

## 二、排查过程与证据

| 查什么 | 结果 | 说明 |
|---|---|---|
| CH340 驱动版本 | **3.9.2024.9**（2024-09） | 不是驱动老 |
| `Get-PnpDevice` 状态 | **OK / Present=True** | Windows 认为设备正常 |
| `ConfigManagerErrorCode` | **0** | 设备管理器里无黄色感叹号 |
| PnP 事件日志 | **无任何 CH340 报错** | 驱动层没记录故障 |
| 设备管理器禁用→启用 | 无效 | 太浅，重置不到功能层 |
| **近 24h USB 枚举事件** | **一条都没有** | ★ 关键证据 |
| 打开端口 | `连到系统上的设备没有发挥作用` | 功能层坏，不是"被占用" |

### 关键推论

```
用户多次断电上电  +  24 小时内零次 USB 枚举  =  板子断电不影响 CH340
```

**CH340 的供电来自 USB 线，不是来自板子的电源。**

所以：

```
关板子电源  →  FPGA 掉电，CH340 仍带电，USB 连接保持
再开板子电源 →  FPGA 上电，CH340 没重新枚举，保持原状态
             →  上电瞬间的电流冲击把 CH340 的串口状态机带偏
             →  Windows 不会主动重新枚举一个"一直在"的设备
             →  卡死，直到你拔线或重启电脑
```

**这也解释了"第一次是对的"**：那时 USB 是刚插上的，CH340 刚枚举完，状态干净。

**也解释了"队友电脑不会"**：多半是他用完就拔线，或者板子/线的供电结构不同。

---

## 三、解决办法

### 立刻恢复（10 秒，不用重启）

```
拔掉 USB 线 → 等 3 秒 → 插回去
```

拔插会强制 USB 重新枚举，相当于给 CH340 做一次硬复位。

### 不想动手：跑脚本

双击 `host/fix_serial.bat`（**右键 → 以管理员身份运行**）。

它做三件事：
1. 列出所有 CH340 设备及其状态
2. 调 `pnputil /restart-device` 重启设备栈（等价于软拔插）
3. 用 460800 打开一次，验证是否恢复

> 注意：脚本里 `pnputil` 需要管理员权限，不提权会报"拒绝访问"。
> 如果重启设备后仍失败，说明状态更死，只能拔线。

### 预防

| 措施 | 成本 | 效果 |
|---|---|---|
| **不用时拔 USB 线** | 零 | 最有效，彻底避免 |
| **关电前先关上位机** | 零 | 减少句柄处于半开状态的概率 |
| 换主板后置 USB 2.0 口 | 零 | 后置口供电稳，前面板/HUB 易掉压 |
| 换一根短粗 USB 线 | 几块钱 | 降低上电瞬间的电压跌落 |
| ~~关 USB 选择性挂起~~ | 已做 | **不是本问题的原因**，但顺手关掉没坏处 |

> 已在 2026-10-21 21:15 把本机 USB 选择性挂起设为禁用（交流和电池都关）。
> 关掉之后问题依旧，说明它**不是**这次的元凶 —— 但它确实是另一类
> "空闲一段时间后串口假死"的常见原因，留着关闭没坏处。

## 四、现场演示要注意

决赛现场如果中途关板子再开，**很可能复现这个故障**。

**对策**：

1. 演示全程**不要关板子电源**。需要复位就按板上的复位键，不要断电。
2. 如果必须断电，**断完电顺手把 USB 也拔插一次**。
3. 随身带 `fix_serial.bat`，管理员运行，10 秒能救回来。
4. 演示前确认串口能打开，别等到讲解中途才发现。

---

## 五、为什么这不是我们代码的锅

上位机打开串口时用的是 pyserial 默认参数，没有做任何独占锁。
报错发生在 `SetCommState`（配置波特率）阶段，而不是 `CreateFile` 阶段 ——
说明**文件句柄能拿到，配置被驱动拒绝**，这是设备侧的问题，不是软件争用。
